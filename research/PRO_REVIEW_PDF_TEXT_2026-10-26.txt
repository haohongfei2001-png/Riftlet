 1. 先定义“成功”，再设计吞噬
 1.1 五种结果必须分开
 本产品真正的事务不是“发了一个粘贴事件”，而是“指定截图进入了用户点击时所指的草稿，而且附件已具备发
 送条件”。此处 ready 只指当前草稿接受该图并完成所需处理，不保证用户以后一定发送、服务端永久保存或模
 型一定使用该图。

  状态                足够说明什么                 不能据此声称什么       裂缝行为


  INPUT_TRIGGERE    输入动作已派发                页面已接受图片        留下在途占位，禁止重复派发
  D


  ATTACHMENT_PR     指定草稿出现了可关联的新附件         上传和后续处理已完成     保留在途状态
  ESENT


  READY             实测有效的完成判据确认该附件         消息已发出或未来必然可用   完成吞噬，从待用队列移除
                    可发送


  FAILED            明确的格式、大小、上传等错误         所有超时都是失败       原位恢复；保留本地原图
                    ，或确定尚未触发的前置失败


  UNKNOWN           超时、导航、观察丢失、崩溃等         可安全重新上传        保留并标记待核对；下次先对

 文件输入控件中已经有文件名、发送按钮 enabled、网络请求返回 200、一个 spinner 消失，都不是通用的独立
 成功证据。已有文字可以让发送按钮提前可用；模型正在回答也可能使按钮不可用；HTTP 成功后仍可能有附件
 处理；占位卡片可能在传输前已经出现。


 1.2 为一次点击建立完整身份
 每次操作应至少包含：assetId、operationId、attemptId、点击时的目标应用 / 浏览器会话、windowId、
 tabId / AXWindow、页面 document 或草稿代次、composer 身份，以及触发前的附件集合基线。

 截图身份、输入操作身份与文件内容 hash 是三件事。相同像素的两次系统截图可以是两个有意条目；一次截图
 的多个文件事件应合并；用户从档案主动再次使用同一图则应建立新操作。不能让全局内容去重误删用户的连
 续截图。

 目标在点击时固定，并在真正输入前再次核对。用户切换到另一对话，不应把排队的图悄悄改投新对话。触发
 前变更可取消或等待；触发后变更通常应进入核对 / UNKNOWN，不能假装失败再重放。


 1.3 重试、并发与恢复
 同一条目在途时的连续点击合并为同一操作。不同图片可以快速点击排队，但同一个草稿的注入必须串行，至
 少串行到能够唯一关联新附件。原生剪贴板路径还需要跨窗口的全局串行，避免不同图片覆盖同一个系统剪贴
 板。

 建议 15 秒作为柔性的等待提示，60 秒作为一档停止积极等待、转入 UNKNOWN 的阈值；这些是待测 UX 参数
 ，不是上传必然失败的时间界线。迟到的 ready 只可作用于匹配的 attemptId，不能吞掉后来重试中的另一项。

 进程在“已触发、未记录回执”之间退出时，重启后必须核对，不能自动重播。没有目标端幂等键时，本地日志无
 法保证严格的远端 exactly-once；正确做法是避免盲目重试和误删，而不是做虚假的保证。

 失败恢复不应重建用户全部草稿，也不应清空所有附件。对于已出现的错误卡片，只有在能够可靠对应本次操
 作时，才可使用该卡片自己的重试机制。用户主动删掉一个已经就绪的附件，是新的用户行为；Rift 不应自动
 不断补回。


 1.4 本地档案与待用队列分离
 成功吞噬意味着从待用队列消费，不意味着删除用户截图文件。建议保留不可变的本地副本和独立档案，原生
 截图源文件不移动、不删除。用户以后可在主窗口主动再次使用、导出或删除。

 图片复制与索引提交应在可恢复的本地事务中完成，再让缩略图可点击。任何导入失败、权限中断、进程退出
 ，都不能产生“看似可用、实际文件不存在”的条目。

 张图片 20 MB 的限制。这说明产品具备图片输入能力，不意味着第三方程序拥有稳定的外部附件 API。[S01]

 2.2 推荐链路
 原生应用负责读取自己的图片副本；已连接的 Native Messaging host 将内容交给扩展 service worker；扩展把
 字节发送给当前目标页面的 content script；content script 定位实际 composer 的附件输入，建立 File /
 DataTransfer，调用经过实测的接收路径；随后只观察该 composer 的新增附件和就绪状态。

 这条路径使用用户现有 ChatGPT 页面自己的登录态与正常上传处理，不读取 cookies、不抽取 token、不调用
 逆向私有上传接口，也不引入 AI API 或自建云服务。

 现有隐藏 input 可能在菜单打开前尚未挂载。适配器必须验证页面原本的挂载方式，不能随意新增一个 input
 就认为 ChatGPT 会接收；也不能为了打开文件选择器而破坏两次操作的目标。

 文件 input 的 FileList 赋值是替换该控件的当前选择。它是否由页面作为“追加附件”处理，必须实测。不要盲目
 把历史 FileList 合并进去，旧文件可能被再次上传。保留用户文本与已有附件应通过只调用追加路径实现，绝不
 使用 Cmd+A、innerHTML 替换或清空附件容器。


 2.3 一次点击如何找到“当前对话”
 只知道 chatgpt.com 标签页存在是不够的。Chrome 的 active / lastFocusedWindow 仅表达一个浏览器上下文
 内的状态，不等于全系统正在使用的窗口；多个 Chrome profile、多个浏览器、普通网页与 Work 页面并存时
 尤其容易错投。[S08]

 建议原生应用只接受点击前确实在前台的受支持目标。扩展为每个页面报告 browser/profile 会话、windowId、
 tabId、frame / documentId、URL / 路由、可见 composer 和焦点状态；应用与扩展共同建立短期目标绑定。
 若只能得到多个可能目标，就保持截图并显示“目标未就绪”，不能自动选择最近打开的后台对话。

 不能仅靠 URL。SPA 可以在同一文档中换对话；新聊天的路径也可能复用。必须同时记录草稿代次和
 composer 的实际元素身份，导航和替换后重新验证。

 点击裂缝不应把 Rift 变成前台应用。Web 主路径也不要求先激活扩展图标。Chrome 的 activeTab 权限需要扩
 展 action、context menu、command、omnibox 等规定的用户调用，外部原生面板点击不会自动获得它。
 [S06] 因而更合适的是一次授权、仅针对 https://chatgpt.com/* 的站点访问；不申请所有站点权限。


 2.4 成功回执：需要“具体附件”的证据
 建立基线后，查找当前 composer 新出现的附件控件，并用文件名、附件标识、操作携带的可用元数据和
 DOM 身份关联本次输入。数量加一不够：用户可能同时手动添加文件；同名文件也不一定是同一个对象。

 对关联的附件，使用当前版本经过验证的复合 ready 判据：存在正向完成状态、所需进度 / pending 已结束、
 没有该附件错误，并且仍在原目标草稿中。MutationObserver 只观察必要的 composer 子树，变化后局部重新
 核对；不高频扫描整个页面。

 网页 DOM 不属于公开稳定契约。因此不能承诺仅靠一条 CSS selector 永远有效。应把定位、插入和完成判断
 封装成小型、可替换的版本适配器，优先使用语义角色、可访问名称、元素关系和结构化状态；为不同语言和
 布局维护小型页面夹具。检测到不认识的界面时保留图片并停止注入，不能退回猜坐标。

 2.6 Native Messaging 不能省略的工程细节
 Chrome 文档规定 host 通过 stdin / stdout 交换带 32 位长度前缀的 UTF-8 JSON。host → Chrome 单条消息上
 限 1 MiB，反向上限 64 MiB。[S07] 一张高分辨率截图经 base64 后常常超过前者，不能把整张图直接装进一个
 JSON。

 建议使用 192-256 KiB 原始字节的分块，附 operationId、序号、总量上限、校验和、ack 与背压。图片拼装有
 内存预算，失败及时释放；host 的 stdout 只写协议，诊断写其他通道。

 浏览器启动独立的、签名的最小 host；host 通过受限本地 IPC 与主程序连接，可选 XPC 或仅当前用户可访问的
 Unix socket。扩展通过 runtime.connectNative 建立端口，原生点击才有可达的接收端；不能假设原生应用可
 直接调用浏览器扩展。

 Manifest 中 allowed_origins 限定自身扩展 ID；IPC 验证本地调用者与操作边界。持久真相留在原生进程的本地
 日志，service worker 断开、重启或浏览器退出不能丢事务。Chrome 的 worker 生命周期和 Native Messaging
 保活规则可利用，但不应依赖常驻全局变量。[S07][S09]

 CDP 可用于隔离的开发验证，不建议作为用户日常主链路。Chrome 已限制默认用户数据目录上的
 remote-debugging-port / pipe，常规方案还会要求特殊启动或另一用户数据目录，损害用户现有会话体验。

 3. ChatGPT Mac 客户端：输入可行，严格回执待证
 3.1 先确认实际产品与版本
 官方 2026-07-09 发布说明已把此前 Mac 应用称为 ChatGPT Classic；官方迁移文档说明原 Codex app 更新为新
 的 ChatGPT desktop app，包含 Chat、Work、Codex，两者可能并存。[S11][S12]

 Codex 团队成员 Romain Huet 的第一人称说明确认 Codex app 使用 Electron。结合官方迁移关系，可以推断新
 版桌面应用有该架构来源；这不是对用户当前 bundle、composer 或 AX 树的直接检查。[S13] 不能沿用“所有
 ChatGPT Mac 客户端都是纯 SwiftUI”的假设，也不能从“Electron”推导出普通 Chrome 扩展可注入它。

 应分别记录实际安装的 bundle identifier、version、build 和窗口类型。新版 Chat、Work、Classic 正常窗口、
 快捷小窗可能需要不同适配；未核验的窗口类型不应默认为已支持。


 3.2 最接近目标的原生候选
 一次点击不激活的 NSPanel → 固定前台应用 / AXWindow / composer → 校验并聚焦正确编辑器 → 写入
 NSPasteboard 图片 → 通过菜单 AX 动作或 CGEvent 执行粘贴 → 观察对应附件 → ready 后消费队列。

 用户不需要自行按快捷键；内部使用系统事件不违反两次操作。但发送 Cmd+V 之前必须知道焦点在正确的输入
 框，不能把 URL 栏、聊天搜索、设置窗口或选中的回答当成草稿。

 NSPanel 使用 nonactivatingPanel，canBecomeKey / canBecomeMain 为 false，点击视图接受 first mouse。
 主应用作为 accessory / 菜单栏应用运行，不通过 makeKeyAndOrderFront 抢焦点。AX 只调用目标实际支持的
 属性和动作；拒绝固定屏幕坐标。[S14][S15]

 图片表示可候选 PNG / TIFF；fileURL 是否被具体客户端接收要单独测试。多种表示属于同一张图片时放在一个
 pasteboard item，避免变成多个附件；多图的 item 行为另行测试。不提供路径 plain text 兜底，否则会把路径
 写入用户草稿。


 3.3 用户原文与选择区域是实际风险
 无选择的输入框与正在选中一段文字的输入框，粘贴图片的行为不一定相同。若图片粘贴会替换选区，应在确
 实支持的 AX 接口下安全折叠选区，并验证没有并发编辑。不能靠出错后重新写回全文“恢复”：那会覆盖用户刚
 输入的新内容。

 原生适配的最小通过条件必须包含：已有中文和 emoji、多段文字、选中文字、已有图片、正在生成回复等场
 景。仅在空白输入框粘贴成功，远不足以承诺可商用的一键附加。


 3.4 AX 是观察机制，不是附件语义保证
 Apple 提供 AX 元素属性、动作和通知，但应用决定暴露什么。AXObserver 可以监听支持的通知，再局部复核
 composer 子树；notificationUnsupported、attributeUnsupported 或 cannotComplete 只能说明观察失败，
 不能说上传失败。[S14]

 如果实际 AX 树暴露文件名、附件节点、进度、错误和完成状态，可建立与网页相似的回执。如果只有一个没有
 状态的图片占位符，则严格 ready 尚不可判断。不能以“延时两秒”“窗口仍在”“发送按钮启用”补足证据。

 3.5 剪贴板恢复必须单独设计
 Apple 的 changeCount 可以帮助判断剪贴板所有权是否已经变化，但不存在供本应用使用的跨进程原子
 compare-and-swap。[S16]

 建议先记录可物化的旧 items / types / data，读前后检查 changeCount；写入图片及自己的操作 marker；确认
 目标已消费必要图片字节之后，仅当剪贴板仍属于本次操作时谨慎恢复。用户期间复制新内容，立即让出，绝
 不覆盖。

 “被请求 data provider”不代表 ChatGPT 消费了图片，可能是剪贴板管理器读取。出现附件卡片是否足以证明字
 节已读完，也需要按 PNG 与 fileURL 方式分别验证。图片已经被安全接收后即可恢复，不必一直等网络上传完
 成。

 固定 50、100 或 300 ms 后恢复会有晚读竞态。旧 lazy provider、file promise、动态数据和 Universal
 Clipboard 语义也无法仅靠字节快照完整重建。不得宣传“100% 无扰动剪贴板恢复”。

 若无法可靠判断消费时刻，较诚实的兼容方式是在首次说明的原生模式中让该图片留在系统剪贴板，用户下一
 次复制立即取得所有权；这仍然是两次操作，却有明确剪贴板副作用。若产品要求剪贴板完全保全，就不能将
 此模式当作已通过的正式方案。

 现行 AppKit 已文档化 NSPasteboard.AccessBehavior 中的 ask / allow / deny 等行为；API 可用版本不等同所
 有 OS 上的具体强制实施时点。后台读剪贴板和截图监听应按目标 macOS 核验授权，不能假定永久免权限。

 3.7 新的官方路线：MCP 草稿接口

 但该接口有关键边界：它是已初始化 MCP App view 与 host 之间的协议；Web 支持矩阵指 Work browser，不

 4. 原生截图无感收录：先尊重系统生命周期
 4.1 系统截图并不在按键后立即落盘
 定义 T0 为用户完成选区 / 触发瞬时截图的时刻；系统生成像素后，可能先显示浮动缩略图；用户还可悬停、进
 入标记或改变保存去向；之后才产生可读取文件。T1 是独立探针首次确认源图完整可读的时刻，T2 是 Rift 的私
 有副本与索引提交完成、缩略图可点击的时刻。

 Apple 官方描述了浮动缩略图及稍后保存行为；Dropover 的官方排障资料也明确其会造成几秒等待，并建议关
 闭该选项以获得及时收录。[S18][S19] 因而不能把 T0 到 T1 的系统等待归咎于监听速度，也不能承诺开启浮动
 缩略图时始终亚秒收录。

 建议保留用户正常的系统截图方式，在一次设置中说明可以关闭“显示浮动缩略图”。不静默改写系统截图目录、
 保存目标或缩略图偏好。用户保留该功能时，Rift 在最终保存后收录；进入标记并尚未保存的图片不会被提前
 当作最终版本。

 本轮未找到覆盖所有原生截图入口、稳定公开且直接携带结果像素的第三方回调。Spotlight、键盘监听、系统
 进程观察都不能普遍提供尚未落盘的最终图片。此结论是公开可用路径的边界，不是对所有私有或未来技术作“
 不可能”判断。


 4.2 推荐混合收录机制
 低延迟主路径是目录 DispatchSource；可靠性来自完整性检查、有限重试和状态重扫。FSEvents / Spotlight 作
 为补漏与重建辅助，而不是把它们误当成每张截图都实时独立发出的消息。[S20][C05]

 目录事件只说明“目录可能变化”，不保证一事件对应一文件。处理 write / rename / delete / revoke，监测目录
 失效与重建；启动时先设监听再扫描，扫描期间变脏则补扫；唤醒、文件事件丢失、根目录变更后重新核对。
 首次安装建立已有文件基线，新截图自动入队，既有历史由用户主动导入；后续重启依据持久化检查点补齐遗
 漏，不把所有旧图重新入队。

 对候选文件，比较 size / mtime / 文件身份，检查 ImageIO complete，以短退避等待写入结束。复制前后再次
 检查源版本，写临时文件后原子改名并提交本地索引。不要每张图串行睡 150 ms，使十连拍累积成 1.5 秒以上
 的人工延迟。

 截图标识优先参考截图元数据和来源，再辅以本地化文件名；不能只认 English “Screenshot”。直接读取
 com.apple.metadata:kMDItemIsScreenCapture 可以作为兼容性探针，但 xattr 的具体存储方式不应承诺为稳
 定公共 ABI。Spotlight 查询可补充分类，但受到索引、通知批处理与卷配置影响。


 4.3 目录变化与权限
 系统截图目录配置可通过 com.apple.screencapture 偏好作兼容性读取；其中具体 key 不是应写死为永久契约
 的公共截图 SDK。启动、唤醒、设置变化线索和有限周期核验时重新读取；发现变更后短期同时监测新旧目录
 ，处理晚到文件。

 4.4 剪贴板截图是可选来源，不能虚报完整支持
 按 Control 保存到剪贴板不会生成普通目标文件。可通过 NSPasteboard changeCount 轮询检测新图，但每次
 只能取得当时的数据；两次轮询之间连续截图覆盖旧图后，changeCount 不能追回被覆盖的图片。

 因此，剪贴板模式只能作为用户开启的兼容来源。它无法保证所有高速连拍零遗漏，也难以区分“原生截图”和“
 从网页复制的任意图片”。应过滤自身 marker、TransientType / ConcealedType 等，避免输入链路重新进入截
 图队列；不默认收集用户整个剪贴板历史。[C03][C08]

 系统截图直接发往 Preview、Mail 等目标，也不等于磁盘来源已产生可观察文件。产品需明确支持的保存去向
 ，而不是悄悄实现另一套截图引擎。


 4.5 格式、排序、去重与恢复
 保留源图片原始编码；用 ImageIO 生成显示缩略图。macOS 的截图格式 / HDR 选项会影响输出，现行 Apple
 资料包含 HEIF / HDR 情形；ChatGPT 的图片格式列表没有覆盖所有这些来源。[S01][S18]

 上传前可生成派生 PNG / JPEG，但必须真正解码、处理方向和色彩，HDR 明确映射到 SDR / sRGB，并检查大
 小；不能改扩展名冒充转换。默认优先保留文字细节；超限时说明原因并保留原件，不无条件强压缩到看不清。

 快速连拍与多显示器截图可能产生多个文件。尽可能以可信捕获时间加稳定递增序号维持顺序；时间缺失或相
 同则按持久化收录序号排序。文件事件到达顺序不等于严格的用户截图顺序；延后保存、标记编辑和多屏输出
 交错时，仅凭文件事件不能始终还原绝对捕获顺序。不要把 firstSeenAt 冒称 capturedAt，也不要编造同一操作
 的分组。

 用卷与源文件资源身份及版本合并重复观察，不能只靠可能复用的 inode；内容 hash 用于完整性或存储共享，
 不自动合并两个独立捕获条目。剪贴板与文件两路也不能只凭时间接近就合并。休眠唤醒补扫，显示器变化更
 新窗口，异常退出恢复 pending / UNKNOWN，不自动重试已触发上传。

 5.6 许可与整体 fork 裁决
 MIT 模块通常可以用于商业及闭源软件，需保留版权和许可。Apache-2.0 同样可商业复用，应保留许可证、适
 用 NOTICE，并按要求标记修改；商标、品牌素材和第三方依赖不是自动随代码授权。Tendedero 的素材例外
 必须单独处理。

 最终采用哪些源码，要按实际复制的固定版本记录归属和修改，而不是列一个模糊“用了开源”的名单。若只借鉴
 公开机制、自行实现，不应假称整个项目是依赖。

 不建议完整 fork。候选项目分别深埋了移动文件、倒序图库、悬停展开、拖放成功、容量删除、OCR 编辑等假
 设；将其改成永久队列、正确草稿和可验证的附件事务，会改到核心数据模型。独立的小应用加少量可审计模
 块，长期成本更低。




 6. 空间裂缝：可直接用于产品讨论的交互规格
 本节为独立设计判断，尺寸和时间是初始规格，需用真实显示器与输入设备校准。Apple 的可访问性建议提供
 基础约束，但并不要求所有 macOS 点击目标都固定为 44 pt；本报告采用较大命中区是为了边缘快速点击。
 [S26][S27]


 6.1 形态裁决：大部分露出，轻微遮挡，不靠悬停展开
 保留裂缝吞噬的空间隐喻，但不推荐只露出一道很窄的图片切片。那会降低识别和命中面积，迫使用户先靠近、
 等展开、重新定位，再点击。悬停虽然不是鼠标按键，却仍是额外的动作阶段。

 建议缩略图始终保持可直接点击的位置和大小，约 90% 以上图像可见，边缘仅遮住 4-6 pt 或图宽的约 6%-10%
 ，取更小值。极窄竖图不能被固定遮挡吃掉。遮挡是表现层 mask，原图和缩略图的缩放本身不做方形裁切。

 6.3 局部露出不等于无限透明命中
 透明窗口仍可能截获鼠标。NSView.hitTest 返回 nil 只解决窗口内部的视图选择，不自动把点击交给另一个应用。
 不能用一张大透明 NSPanel 覆盖整条屏幕边缘，然后假定空白都穿透。[S28]

 建议装饰线使用 ignoresMouseEvents=true 的窄窗口；每个可见截图使用边界明确的小面板或经过验证的命中
 结构，行间空隙不放接收输入的窗口。固定 48 pt 格子内的空白可为该条目命中，格子外应穿透。

 可见项数量有限，面板复用；不为全部历史各开一个窗口。窗口级鼠标开关如果依据 move 动态切换，需要验
 证首次点击是否丢失。小面板方案也要测 WindowServer 成本，不能只因代码简单就无限扩张。


 6.4 吞噬、在途与重生
 点击后立刻给出轻微响应，建议首次反馈不晚于约 80 ms；100-140 ms 内向裂缝内移约 6 pt，随后留下细小在
 途标记并保留队列槽位。网络上传期间不循环夸张吸入，不显示虚构进度百分比。

 收到真实 ready 后再用 180-240 ms 完成裁切 / 压缩式吞噬，随后下方自然上移。明确失败则 160-220 ms 反向
 恢复原图；UNKNOWN 使用安静的状态点和说明“未确认，截图已保留”，不能画成明确红色失败。

 成功后的重排建议约 140-180 ms，但指针悬停或鼠标按下时要保护目标。鼠标按下捕获 assetId，直到释放都
 不能换成下一张。新增图、失败恢复、溢出切换、屏幕变化，也不能让另一张图在点击中途顶到原位置。

 6.5 FIFO 与无限历史的空间矛盾
 数量能全部容纳时，最早在上，新图在下。成功后删除队列成员，保留其他项相对顺序。

 最新若干项”，所有可见图仍按时间升序，最新图始终直接可点；隐藏的中间历史通过滚动或主窗口访问。

 这个方案保留即时复用的两次操作，但不能宣称任意历史图也永远只需直接一击。不要自动删除最旧截图、把
 全部缩小到不可点，或让滚动永远停在过去导致新图不可见。行的布局变化仍须遵守指针稳定规则。


 6.6 全屏、Space、多显示器与静止策略
 窗口采用 nonactivatingPanel，按系统版本核验 canJoinAllSpaces、canJoinAllApplications、
 fullScreenAuxiliary、stationary 等行为。Apple DTS 在 2026 年公开案例中给出特定窗口级别和 flags，在
 macOS 26 的部分全屏应用中验证可见；这只是该案例的实测，不是本产品覆盖所有应用的证明。[S22]

 默认固定在一块显示器的外缘，用户可一次设置镜像到其他显示器；镜像共享同一队列和操作 ID，不复制上传。
 使用稳定显示器标识，处理 scale、visibleFrame、菜单栏、Dock、拔屏和合盖变化。拔屏后迁移到有效主屏，
 不依据数组下标误认显示器。

 选择能通过实际矩阵的最低窗口层级，不用 screenSaver 级别强压所有系统界面。锁屏、系统授权和安全界面
 应让出；普通全屏应用的覆盖需单独验证。避免依赖私有 CGS Space 查询。

 有待用截图时保持静止，不因短暂鼠标离开隐藏；空队列只留约 12-20 pt 的安静线段或由用户关闭。点击非
 ChatGPT 场景不偷投后台上次会话，而是保留条目并说明目标未就绪。


 6.7 主程序完整浏览
 主窗口提供按日期分组的截图网格、全图预览、待用 / 已使用状态和主动再次加入队列。内部存储使用唯一 ID
 ，显示名称可为“2026-10-26 14.32.18 - 003”；同秒多张用序号区分，保留来源时间和首次发现时间。

 这不是额外的日常上传步骤，而是处理完整历史、重复使用和明确删除的地方。首版不需要 OCR 搜索、标签体
 系、AI 命名、编辑器、收藏工作流或云同步。用户删除源文件不会使已完成导入的私有档案突然失效。

 9. 独立产品改进与最终裁决
 9.1 应保留
 保留系统截图习惯、极细边缘形态、等比小图、最早在上、一次点击进入当前草稿、绝不自动发送。保留明确
 成功后的吞噬和失败后的原序恢复。保留全本地处理与少权限原则。

 这些约束具有辨识度，也能控制产品范围。现有 shelf 产品已证明“截图在屏幕边缘暂存”不稀奇，真正能形成差
 异的是无需拖放、可靠附加、正确回执和用户内容保全。


 9.2 应修正
 明确点击后的动画语义是“立即响应，在途可见，ready 后消失”，避免提前表现成功。建议采用“大部分固定露
 出，小面积遮挡”，而不是必须靠近展开的小切片。明确系统保存前后的延迟，以及各类截图来源的能力与权限
 边界，不把未知情形包装成全覆盖。

 明确成功仅消费待用队列，原图与本地档案继续保留。超时进入 UNKNOWN 并先对账；最新与可见队列直接点
 击，完整历史由主窗口承接。有限边缘面积无法让无限历史都同时保持一击可达。

 删除固定坐标、固定延时宣告成功、私有 CGS 作为核心、清空用户草稿、自动重放未知操作、自动删最旧文件、

 首版推迟 OCR、AI 标签、编辑器、复杂搜索、云同步、账户系统、通用多目标上传平台、远程脚本热更新、夸
 张动效和声音。它们不会帮助证明最关键的两次操作，反而增加安装、权限、性能和维护成本。


 9.4 四个明确回答
 现在是否具备进入正式开发的条件？ 已具备进入有界最小技术验证的条件；尚不具备无条件投入完整产品开发
 的条件。网页主方案须通过实际输入与 ready 门槛；Mac 严格支持须取得实际 AX 或更可靠官方路径的回执证
 据；截图自身排除和系统缩略图延迟也需要明确支持边界。

 哪些现成技术值得直接复用？ Sukurini 的 FolderWatcher 与 ThumbnailLoader 机制，Screenshoss 的完整文件
 检测与测试案例，Tendedero 的非激活小窗口结构，Maccy 的键盘布局 / pasteboard 表示，Oracle 的附件基线、
 DOM 身份回执和导航保护。使用固定版本的小模块并重写与产品契约不符的部分。

 哪个环节最可能使项目长期无法交付？ 跨版本识别“这张图已经在这一草稿准备就绪”，尤其 Mac 客户端。如果
 一直只证明粘贴已发送，就会陷入误报成功、超时重试、重复附件与焦点补丁循环。第二个危险是把自身窗口
 不可被所有系统截图捕获当成一个现成 API 开关。

 怎样以最少工作做出真正稳定、精致而不同的产品？ 先证明目标绑定、附加与回执；选一个通过门槛的平台发
 布严格体验；用独立 AppKit 小外壳整合成熟底层模块；只做档案、FIFO、精确状态和克制动效。若 Mac 回执
 未过门，保留清晰的兼容边界，不让网页体验为了统一实现而退化成盲粘贴。差异来自可信的一次点击，而不
 是更多截图工具功能。
