# 1.0.5 产品修正方向

本页是本轮产品裁决，供 Codex 直接实施；实际完成度由验收决定。它修正旧质量文档中将“清理永远待定”“START 后失败恢复留给未来”当作长期边界的做法。当前发行事实仍按 [AUDIT](AUDIT.md) 区分。

## 1. 产品仍然是什么

Riftlet 是轻量的桌面截图工作队列：正常截图 → 边缘微图 → 一次自然点击 → 图片进入点击时正确的 Chrome ChatGPT 草稿 → 用户自己发送。默认使用托盘，保留风铃、微缝与旧用户合法外观。它首先解决截图使用过程，不变成带几十个选项的控制台。

- 托盘保持两列、最多四个内容槽、现有顺序与滚轮浏览。截图按钮的既定位置、展开独占一行并推动其它内容的逻辑保留。
- 当前接收有正面 START 证据便收起；不等上传终态才吞噬。明确失败恢复到可处理状态，结果不明保持诚实且可找回。
- 用户原有草稿文字、选区、附件保持；无可用目标时给一条短反馈并保留图片。不增加每次选择对话、二次确认、拖拽、粘贴或必须记快捷键的步骤。
- 图片显示与附加权限分开；重新显示图片不等于许可重复上传。旧 UNKNOWN 不阻塞后来的独立截图。
- 本版不扩浏览器/服务。Nearpane 的任意文件中心、下载集中存放、双入口托盘讨论不能直接当作 Riftlet 1.0.5 已批准的新功能，也不把这些待定布局覆盖到现有托盘。

## 2. 设置：保留四页，真正收口

不再创建第五套设置架构。使用当前 SettingsProductHost、现有状态 owner 和原生控件；减少呈现的维度、统一行为，保留旧数据兼容。

| 页面 | 主层内容 | 条件出现/管理入口 | 应退出普通页面的内容 |
|---|---|---|---|
| 通用 | 登录时启动；版本与检查更新；自动检查更新 | 仅实际登录项批准或更新失败的必要下一步 | build/hash、每日重复正常状态、技术解释 |
| 外观 | 桌面显示；系统/浅/深外观；托盘/风铃/微缝；真实预览；屏幕位置；托盘透明度和相机颜色 | 多屏或已选屏幕断开/实际位置与偏好不一致时显示屏幕选择；数量与动效置于次级组；旧自定义仅简短状态与可撤销恢复推荐外观 | 像素/pt几何墙、色相强度、同一项滑杆+数字双编辑、全局重置 |
| 截图 | 系统截图位置与必要授权；内置截图入口/默认方式；闲置收起；仓库与存储摘要 | “管理…”处理资料；真正拒绝后才显示屏幕权限修复；内置功能关闭时收起其从属项 | 未使用即警告、普通用户输入小数分钟、只有容量却无动作 |
| 帮助 | Chrome 当前状态与唯一下一步；简短使用说明；反馈 | 可展开诊断，必要的旧兼容维护入口 | 无故障时一组修复按钮、多个重复检查、内部事务说明 |

### 具体减法

1. 新用户保留 1.0.4 三图托盘默认。每页数量用一个符合实际形态上限的离散选择，普通托盘不能承诺5–10张。
2. 闲置收起提供“关闭、1、2、5、10分钟”；老用户1.75等合法值继续准确显示/生效，只有主动选新值才改变。收起与删除是两件事。
3. 旧几何字段继续读写兼容。普通层显示“沿用自定义外观”；“使用推荐外观”仅修改说明范围内的视觉字段并可撤销。形态、屏幕、归档、原图不被顺带重置。无需为可撤销的颜色/布局操作反复确认。
4. 新有效选择立即保存，失败在该项旁用短句说明并给重试；页面切换、无关字段和隐藏旧值不能阻止当前有效设置。不要新增“应用所有设置”总按钮。
5. Chrome 设置始终根据真实情况给一个下一步：打开Chrome、授权、开启相应浏览器选项或已连接。成功常态安静，不要求用户反复“确认安全”。
6. 正常菜单保留四项；只有需要处理的实际情况增加状态和恢复动作。收录暂停或桌面隐藏应能直接恢复，不依赖悬停 tooltip。

### 视觉完成度

- 导航与窗口工具栏统一；页名只承担一处主要标题，避免窗口/页签/正文三个同等标题。用少数内容分组、分隔线和稳定对齐表达层级，不靠大块空白或给每行再套卡片。
- 保留当前最小窗口可用性，默认窗口从内容决定，正文在宽窗口内保持约560–720pt阅读列。正常行紧凑，长文本自然换行；去掉所有分组固定50pt的机械规则，不缩按钮热区来节省空间。
- 外观页让真实预览和它控制的内容处于同一组。颜色仅改变已定义的相机实体；透明度仅改变托盘背景；缩略图、镜头和操作键不能被整体染色。预览与实际桌面共用渲染。
- 正文通常13pt，影响理解或恢复的说明至少12pt，使用系统语义文本/背景/分隔色。浅深与高对比均能辨认；普通分组标题不统一染成强调色。
- 按真实中英窗口看整体密度、比例、对齐和控件光学居中。`clipping=false` 只是底线，不能作为“顶级设计已完成”的唯一判断。
- 不把全新视觉语言覆盖到托盘、风铃、微缝，不用紫色品牌改造或新的侧栏替代已确认形态。

## 3. 接收、失败与历史：用户看得懂，内部事实不失真

| 实际事实 | 用户看到 | 可以做 | 软件不能擅自做 |
|---|---|---|---|
| 还未外部输入，明确失败 | 图片留在/回到桌面，一条原因 | 修复后再次点击，按新点击冻结目标 | 丢图、要求用户猜去哪个页面 |
| 当前文件有匹配 START | 立即收起；历史“已交给 ChatGPT” | 查看原图；必要时查看原对话 | 宣称服务端上传完成或消息已发送 |
| START 后同一附件明确终止失败 | 回到需要处理的图片状态 | 具备可靠终止证明时由用户点击重试 | 自动上传、将无关附件错误套到这张图 |
| 输入是否发生不明、连接断开、目标离开 | “需要确认”及有效下一步 | 看图/查看可验证的原对话/继续只读观察 | 超时改失败、清 UNKNOWN、自动重传 |
| 用户主动收起/移出 | 历史可查，状态仍准确 | 恢复显示；符合输入资格才可再次附加 | 迟到回执反复强制弹回 |
| 本地副本缺失或待收录 | 清楚说明并给查看/恢复动作 | 通过已验证原件恢复/补收录 | 伪造成功或清库重建 |

生产策略当前没有接纳安全重试/终止证据的profile。若要让确认失败的图片重新可点击，W2必须把确切profile、终止证明、反例、真实能力声明一起交独立审查，并按既有准入流程处理；不是仅把safeRetry改成true。本规划不修改门禁、生产能力或旧回执；不能借新策略追认旧UNKNOWN、跳过目标/终止验证或将泛化自动重试开放给所有输入。

明确区分历史 START 回执与实时上传状态。对失败进行有限、只读、精确绑定的后续观察；没有变化不写库，失效目标按预算暂停，不再每5秒无意义重复。观察不依赖“允许自动重试”之类用户开关。

历史普通筛选用少数任务分类：**全部、桌面中、需要处理**。已交给ChatGPT、已收起、旧的已完成事实用条目/详情说明；状态轴不与桌面可见性混在一个七选一筛选里。继续全库搜索、列表/网格与原UUID；可用的恢复动作就在项目旁，不要求找 Finder 才知道下一步。

## 4. 资料生命周期：软件负责垃圾，用户掌握资料

“永远不能清理”不再是 1.0.5 的方向。本轮直接实现完整的管理能力；开发与验证使用隔离资料，不对用户现有生产库执行清理。

| 对象 | 1.0.5 规则 |
|---|---|
| 用户系统截图原件、外部文件 | 只读；Riftlet 的清理不删除或修改它们 |
| 正在导入/交接、UNKNOWN、明确失败待恢复、唯一可用原件 | 不进入自动垃圾清理；在管理中说明占用和可用动作 |
| 无标注的内置截图多份副本 | 收录持久成功后保留一个权威媒体归属；去重不能破坏崩溃恢复 |
| 标注前原件/标注结果 | 建立关联并可找回，按资料管理；不永久藏在两个无人知道的目录中 |
| 确认可再生缓存/无主且无价值的临时残留 | 自动维护，用户无需设置开关；活跃任务/完整待恢复捕获先排除 |
| 配置恢复备份 | 同次/同内容失败不无限复制；保留必要的可恢复版本，已失效重复按上限维护 |
| 私有截图副本 | 有简单留存规则和主动批量清理；操作前给准确可清理集合、数量、空间和恢复方式 |
| journal、去重身份、交接回执 | 与媒体生命周期一起处理；删除后不重新收录、不被恢复流程复建，不盲删防重放证据 |

### 默认与迁移

- **自动维护确定的临时垃圾始终由软件完成。** 不再让用户维护 staging/journal、配置备份个数或“安全等级”。
- 本轮新增裁决：全新档案的副本整理推荐默认30天，可在“管理…”中选30天、90天或一直保留；只自动整理已收起、无未决操作、外部原件仍可验证可用的重复副本。唯一图片、正在使用的图及需恢复项目继续保护。明确说明到期副本将从仓库移出、系统原图保留，不承诺清理后的完整截图历史仍永久可预览。
- 升级已有用户时，整个已有档案（包括升级后的新截图）继续原留存政策，直至用户在管理中主动选择；30天默认仅自动适用于全新档案。在管理入口显示现状和选择，不强弹阻断引导。旧记录只有用户明确选择将规则应用于现有历史后才进入规则；不能在安装升级时静默改变既有承诺。
- 自动整理的前置条件是为新收录持久保存足够的来源引用，并在清理提交前验证外部原件可读、同一发生身份及原SHA；当前 ImportedAsset 没有源URL，不能假装已经具备。旧记录无可靠引用就跳过，不猜路径。采用最小方案：清理项从普通仓库移出，保留必要删除/去重记录与可恢复删除身份，不把历史改造成依赖外部文件实时可用的新图库，不做同步或自动再导入。原件随后移动/删除时，撤销只能按实际仍可找回的材料处理，不能误认同名新文件或虚构预览。
- 自动整理和批量清理均排除活跃导入、在途交接、UNKNOWN及明确失败待恢复项目；不能通过删资料清除回执或授予重试权。无法验证原件的非保护项目及仅存一份的非保护资料，仍可由用户明确、可恢复地删除，唯一原件必须清楚标示。
- 批量删除应可撤销/找回，优先使用系统废纸篓或既有可恢复机制，避免再复制整个库。界面区分“预计可清理”和“已释放”；移到废纸篓后空间可能要在清空废纸篓后才真正释放。只在唯一资料被不可恢复删除时做必要确认。
- 用最小一致性状态保护删图、journal、去重和恢复顺序。单一资料清理中途失败可恢复，不把删库重建或反复备份整库当容错方案。

W3先闭合待收录恢复、内置副本归属、确定垃圾维护、可恢复批量删除和重启一致性，再接入最小留存调度；不为30天参数新建外部原件管理框架。验收包含外部原件在整理后移动/删除的反例。

这不是承诺所有用户资料总量永不增长。目标是没有无主垃圾和无意义多副本，增长有解释、有管理方式，长期运行成本不跟所有历史同步膨胀。

## 5. 工程减法的边界

当前产品合同与实际版本状态只维护一份活动入口；旧证据按SHA留存，不参加新任务推理。保留证明有价值的测试与签名/身份/事务保护，删除无消费者的死路径和重复当前说明。不要按文件行数机械拆架构，不写一个新的设置框架、资料框架或“全能事务引擎”。

最先删掉的应是无效重复工作和用户不需要的决策，不是正确的保护：目标冻结、一次输入、私有媒体核验、未知字段兼容、签名更新继续有效。校验失败只影响相关功能/项目；可逆操作用默认和撤销，无须一层层用户批准。
