## 完整截图仓库

1.0.10 中，用户没有附加目标时点过的截图，在 20 张更新截图进入最近历史后仍保有原图，但完整仓库无法恢复它。隔离 SQLite 复现和修复后的回归均覆盖这个场景。现有「恢复到托盘」按钮只对能确认从未发起附加的这类截图增加恢复资格。恢复本身只改变本机可见性；用户另行点击才会创建操作。有保留操作、START 或 UNKNOWN 的截图继续遵守原规则，最近历史容量仍为 20。[缺陷复现与修复](https://github.com/haohongfei2001-png/Riftlet/pull/134)

## 真实网站

使用签名 App、普通浏览器、专用临时对话及测试窗口的真实系统截图。下表中的成功附加均核对了原草稿、新附件、浏览器解码后的图像像素和持久化 START。START 表示页面已接收本次附件，服务端最终处理状态另计。

| 用户场景 | Google Chrome | Microsoft Edge |
| --- | --- | --- |
| 单图及连续两张不同截图 | 正确草稿收到各图，点击后退出活动托盘，可在历史中找回 | 同项通过 |
| 同一历史截图主动再附加 | 原文和已有附件保留，每次明确点击各有一次文件输入及 change | 同项通过 |
| 无目标点击，随后从最近历史重选 | 首次零操作。目标就绪后，重选原图成功，已有附件与非空原文保留 | 同项通过 |
| 原截图被 20 张新图挤出，从完整仓库找回 | 「恢复到托盘」前后零操作，随后在保有旧附件的草稿内另行点击成功 | 「恢复到托盘」前后零操作，随后另行点击成功 |
| 发送控制 | 零发送、零表单提交，未观察到自动重放 | 同项通过 |

每款浏览器的完整仓库测试均采集了原图及 20 张更新的真实系统截图。准备满额历史时通过产品现有队列接口选入这 20 张图。恢复原图使用签名 App 中实际的仓库按钮，随后独立触发托盘的原生 AppKit 点击。两款浏览器均验证资产身份、原 PNG 和唯一 START。最近历史重选测试中，每款浏览器各有两次输入和两个 START，分别对应原有种子图和显式重选的原图。

### 新开草稿中的早期观察

- Chrome 有一次点击时适配器尚不可用，未创建操作。另一轮已发生一次输入，页面出现对应的移除按钮，但未取得可比对的预览或 START，结果保留为 UNKNOWN。还有一次在投递前检测到原目标变化，未写入文件。
- Edge 有一次在输入后未取得可归属的新卡，结果保留为 UNKNOWN。另一次点击时页面的四个文件输入仍全部禁用，未产生文件输入。
- 这些轮次的原 PNG 均保留。后续成功轮次使用新的明确选择，独立核对文件输入、附件和旧记录。没有观察到错误投递、重复输入或自动发送。
