# Riftlet 1.0.6（40）候选验收

**放行结论：暂缓扩大推广。** 实际登录及匿名草稿的首击均已通过，真实可见异常也完成了人工核对与重新附加。尚未验成的是同一张图先取得 Riftlet 的正面接收回执（START），随后在 ChatGPT 出现明确错误，再由 Riftlet 找回。公开 Release、官网和 stable feed 目前均提供 1.0.5（31）。

产品提交为 `65398096092e739bb9581244961112b572006465`，基线是 PR #114 合并后的 main `9fd8ad15fca043915069904113e5fb67d82b4948`。本报告仅在明确标注构建号时引用历史结果。[38 的原始报告](https://github.com/haohongfei2001-png/Riftlet/blob/bd839672b06f161aaa05b1cdf45e727792567707/docs/releases/1.0.6/RC_REPORT.md)

## 上一轮问题的修复

- **首击超时。** 38 的匿名测试里，读取窗口与标签耗时 116.94 ms，后续 URL 查询与它共用 150 ms 总预算。40 在鼠标按下时向同一个已固定 Chrome 进程提交两条只读 Apple Event，核对窗口、标签与 URL；后续操作仍按原页面及编辑器复核。两个标签 ID 冲突或窗口身份无法固定就退出。对只缺可选 URL 的回复，只能按已经固定的绝对窗口和标签读取。隔离 Mac 的 12 组交替测量为串行 31–34 ms、新路径 15–17 ms；5 次故意在查询间换标签均正确拒绝。[原生 Chrome 取证](evidence/click-snapshot-native.json)
- **原卡失败。** 保留正面接收事实与当前错误的独立身份。已存在的进度条须在相同量程上实际推进。只在原草稿、原成员与完整文件身份相符时接纳该卡可见的失败状态。原卡出现别张图或被复用时，旧操作继续保留原有事实。39 的完整回归发现旁边出现重复视图时会漏报原预览自己的错误，已在 40 修复。[真实 Chrome 本地双图正反例](evidence/card-identity-chrome.json)
- **窄窗搜索。** 搜索框显示“搜索 / Search”，VoiceOver 使用“搜索截图 / Search screenshots”。在 106 pt 宽度上，文本区实测为 78 pt，两个提示分别宽 25.8 与 42.1 pt。

## 同一签名候选的验收

**V1 · 已登录真实草稿。** 冷首击、暖首击与三组双图共 8 个独立操作，各取得自己的 START；同一份未发送草稿上能看到顺序正确的八张不同测试图，原文字及选区均保留。三组按下间隔为 711.4、645.2、664.3 ms。点击至观察到收起的冷/暖上界为 1.863/2.434 秒，八次中位数 2.349 秒，p95 及最大均为 2.988 秒。从另一空白标签通过仓库能精确返回原草稿。[逐次时序](evidence/v1-host-build40.json)

匿名 Chrome 的独立冷首击也进入正确草稿，一次输入产生一张可见卡和一个 START。鼠标按下时的原目标定位为 91.57 ms，至观察到收起的上界为 2.507 秒。切换标签并重启 Riftlet 后，核对与返回均找到原卡；关闭原标签后准确提示找不到原草稿，未新增操作或 START。[匿名草稿与重启实测](evidence/guest-a-build40.json)

**V2 · 真实异常与用户处置。** 先在无草稿的空白标签点击一张图，图继续可见，8 个操作与 8 条 START 均未增加。随后在登录草稿中，一张测试图显示“上传未成功”。旧操作为 UNKNOWN，没有 START。通过仓库核对并确认再次附加时，操作数不变；恢复网络后，由用户再点一次，产生独立的第二次操作和一份 START。原失败卡和旧操作仍可辨认。另一份新的专用草稿仅对后处理请求启用 Chrome 自带请求阻断，Network 确认恰好命中一次。网页为该图显示了“上传未成功 / Retry”；截至 +105.3 秒，均无该图的 START，+16.6 秒已记录 UNKNOWN。重启并对原操作手动核对前后，11 个操作与 9 条 START 均未增加。**从已取得 START 到同卡真实失败的找回仍为未验证。** 在同一网页程序的受控 Chrome 测试中已观测到该顺序，邻卡保持正常。两类证据分别记录。[真实异常记录](evidence/v2-host-build40.json) · [受控双图反例](evidence/card-identity-chrome.json)

**V3 · 本地资料治理。** 普通管理窗展示 24 份可移出的副本，含 6 份没有已核实外部原件的副本和 4 份有真实附加记录的图片。用户确认后这些副本进入系统废纸篓，正常退出、重启并找回后，29 张图的身份及字节、8 个原操作和 5 份 START 均保留。无 START 的旧 UNKNOWN 与两份预输入失败图在清理期间可用。[隔离 Mac 的资料回执](evidence/guest-a-build40.json)

**V4 · 普通 App 界面。** 全新资料下选择“稍后”后退出重启，欢迎窗保持关闭。首次使用内置相机时，缺权限提示能打开 macOS 的“屏幕与系统音频录制”面板。授权并实际重启后成功截图。实拍覆盖中英文四页设置、浅深色、资料管理、仓库列表和网格。默认仓库为 808 × 492 pt，最小窗为 680 × 480 pt。最小窗下聚焦搜索时，“Search”完整可见。管理窗在新增一份可找回资料后自动从 0 刷新为 1，用户找回后回到 0。双语标注经画框、撤销、保存失败重试与退出确认，原图保留。VoiceOver 字幕实际读出“Search screenshots Search, search text field”，中文搜索、状态/日期选择器和网格位置也有读屏字幕。[原生界面记录](evidence/guest-b-build40.json)

**V5 · 更新。** 公开 1.0.5（31）与同营销版 1.0.6（35）通过隔离签名 Sparkle 清单实际安装并重启，运行中二进制散列均等于正式 DMG 内的 App。两次比较均通过 SQLite 完整性、原文件、旧操作、目录书签和反馈草稿检查。[升级前后对照](evidence/v5-upgrade-build40.json)

同一正式 DMG 从公开 1.0.3（25）手动覆盖原安装后启动；12 份原文件哈希、旧行、书签、反馈草稿均保留，SQLite 检查正常。[手动升级记录](evidence/guest-b-build40.json)

**V6 · 普通 App 的长期使用初测。** 在 2 核、4 GiB 的隔离 Mac 上装入 1,000 张实际 PNG 后，资料管理首屏显示“1,000 份”的观察上界为 2.108 秒，含输入、截屏与 OCR。核验资料时新增 20 张，收录延迟 p50/p95/最大为 416/674/1,001 ms。更改规则并打开历史时再新增 20 张，对应为 387/1,837/3,151 ms。40 张全部入库，各有独立身份，私有副本与外部原图的哈希相符。最慢的一张约 3.15 秒才可用。覆盖首批的 63.6 秒进程采样中，RSS 峰值 133.1 MB，用户/系统 CPU 分别为 6.59/2.47 秒，物理读写分别为 434.9/13.8 MB。本次为千图短时并发取样。[普通进程测量与范围](evidence/guest-b-build40.json)

**平台覆盖。** 签名安装包的两个架构均已执行自检。实机界面与官网对照之外，物理 Intel Mac、macOS 13 实机、多台物理显示器以及 Chrome 自动化权限从拒绝到再次授予的完整系统交互，本轮均为 NOT_RUN。远端 main 分支保护仍由 #83 单独跟踪。
