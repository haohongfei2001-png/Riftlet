## 原草稿显示上传失败

49 的登录 Chrome 草稿中，一个约 6.1 MB 的测试 PNG 进入了原草稿，出现具名进度，Riftlet 尚未记录 START。只对该测试标签临时离线后，原卡显示“上传未成功”、指名本图的重试与移除按钮。恢复网络后在普通截图仓库重新核对，仍只显示“结果待核实”。当次有一次文件输入、零次再次输入、零发送。

52 在原稿记住本次输入前已经存在的卡片。只对本次操作新出现、可见且同时具备完整文件名、该文件的明确错误、可用重试按钮和同卡移除按钮的成员，记录“原草稿报告上传失败”。这一记录不产生 START，也不授权重传。在资料库可以核对原图、选择再次附加或标为已处理；首次操作与历史回执仍保留。原稿、文件、卡片或调用身份不符时，保留待核实。该版本也改用内核的进程出生信息及可执行文件来核对已经捕获的浏览器实例。在 51 上，Chrome 真实快速双图曾在 begin 阶段拒绝，前后台记录中的 PID 和出生信息未变。独立不访问页面的采样观察到了 Launch Services 的短暂缺失。[独立受控复核](evidence/independent-card-52.json)

复核真实浏览器的元素树后，还发现图片与文件名下方有第三个空的装饰边框。52 会拒绝这种原卡。53 识别该边框，同时拒绝带交互、内容、无障碍名称或额外成员的节点，并区分可键盘操作的重试按钮与显式禁用按钮。资料库的内存筛选与数据库筛选也对这种原卡失败给出一致结果。[独立反例与实测边界](evidence/independent-exact-card-53.json)

## 点击时的权限检查

49 的 Chrome 三组真实快速双图成功，首次冷启动仍有一次原生读取标签页超时。Edge 也有一次在原生读取阶段拒绝，均在文件输入前。另行记录的四次系统被动权限查询耗时约 21–455 毫秒；这些并非失败点击本身的分段计时。51 使用 macOS 的 `kAEDoNotPromptForUserConsent`，让每个真实的 Apple Event 直接接受系统权限裁决，设置窗中的显式授权按钮仍可申请权限，首次未授权与明确拒绝各显示对应的恢复入口。原窗口、标签、文档和编辑器的 150 毫秒绑定边界保持不变。失败诊断能区分发送、接收与原标签 URL 核对。[独立复核](evidence/independent-consent-51.json) · [49 本地资料及找回](evidence/storage-49.json)
