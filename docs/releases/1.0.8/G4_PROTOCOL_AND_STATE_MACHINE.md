# G4 原草稿的失败、未知与显式恢复

Riftlet 将本机文件输入、网站开始显示附件、浏览器传输结果和网站的明确失败分别记录。旧操作一旦可能写入过文件，其后续查询只读。用户可以找回磁盘原 PNG。只有符合下列实证条件的新点击才可再次附加。

## 已经观察到的实站状态

签名 build 59 在独立 Edge Temporary Chat 对每张原图执行一次产品点击，分别在原生 send 后、上传部分字节后和浏览器报告上传完毕但尚未观察到响应时取消了一个已识别的客户端 XHR。三个故障均收到浏览器 abort 与 loadend；服务器最终是否存储文件仍未知。三个草稿均未观察到属于该操作的明确错误卡，原图和 SQLite 原记录均保留，也没有第二次输入。另一次大图的创建信息不匹配，探针退出，取消次数为零。[三种策略及独立收据](evidence/build59/g4-final-strategies.json)

| 证据 | 可确定的状态 | 转移条件 |
| --- | --- | --- |
| 原生 setter、input/change 与原操作相符 | 本地输入已触发，结果可能未知 | 保留 PNG、原 invocation、原目标和历史 |
| 原草稿中的新附件成员通过图像归属校验 | 记录一次持久化 START | 继续按原操作只读查询；START 不证明上传完成 |
| 原操作、原 PNG 和原草稿的明确失败成员仍可复核 | G4-A 的现场前提成立 | 可提示显式找回；再次输入需独立点击和最终页面核验 |
| 可归因的真实服务器 4xx 加原卡消失 | G4-B 的待复核样本 | 需要独立书面等价性裁决。受控网关响应单列 |
| 受控客户端中断、卡片消失或上传结果未知 | 保留 UNKNOWN | 仅在 G4-C 的原草稿检查通过且用户明确接受可能重复时，才可创建另一次操作 |

对 build 59 的自然及三种受控客户端故障，G4-A 的原错误卡和 G4-B 的真实服务器 4xx 均无合格样本。受控协议回归和新候选的产品实现须与同包实站结果分别记账。[原卡审计](evidence/build59/g4-final-card-observation.json) · [受控 HTTP 证据](evidence/build59/g4-http-control.json)

## G4-C 的页面检查

1. 在原 PNG 的实际 setter 之前，页面记录原编辑器所属附件区域的基线。此前的附件按节点和顺序保留，附件内容及关键标识在原地发生变化也会使基线失效。页面仅保存有限生命周期的本地观察状态。
2. 输入之后，须在这一原附件行观察到新出现的可见原卡，其移除控件带完整操作 UUID。已知的 PNG 与同 UUID WebP 显示名都参与相互竞争检查。单凭空白草稿、移除 DOM 节点、页面地址或标题均不足以建立可恢复性。
3. 找回使用 SQLite 的旧操作、原 invocation、asset、尝试序号、PNG SHA，以及既有 START 或错误收据。历史查询和旧页面通道只有读取权限。新点击须提供不同 clickBindingID 和原浏览器出生身份、原窗口、标签、Document、编辑器、草稿代际。仅重新打开相同地址无法重新构造凭据。
4. 若旧结果未知，要求曾经识别的原卡已经离开，并且原区域剩余的成员完全匹配基线。旧卡、进行中的可见成员、无法归属的新卡、缺失的原附件、重建的旧附件、消失的 Document 或不可识别的布局均令检查失败。若 SQLite 已有具名失败收据，则要求当前仍能识别同一错误成员，并核对对应的 START 或失败 invocation。
5. Core 在准备新操作前进行只读页面检查。新 begin 绑定同一前驱，最终在一次 setter 中、真正进入文件输入前再次核验。两次检查之间出现旧卡或不明附件会令新输入提前退休。新操作使用新 invocation，并以原 PNG 的完整字节走既有一次性投递路径。
6. 显式操作只允许附加，原页面没有自动发送或表单提交路径。成功与否按新的原卡及独立 START 核验；旧记录的历史含义保持不变。再次输入的清晰提示尤其重要：浏览器只可证明观察期内的页面状态，无法保证服务器未接收旧请求。

协议范围限于 Riftlet 自有代码与公开可见的草稿编辑器、附件、文件输入和用户选择。恢复检查在原页面本地完成。 原始截图、草稿内容、签名地址和浏览器认证数据均不写入公开收据。[实站和快照验收顺序](G4_AUTONOMOUS_RUNBOOK.md)

## 网络事件与页面事件的归属

build 59 对一张 5,516 字节的系统 PNG 做了正常上传标定。浏览器先用 fetch POST 创建文件，文件名字段为 `file_name`，返回 HTTP 200 和 `upload_url`。随后 XHR 用 PUT 发送同一个 File，整份请求体 SHA-256 与原 PNG 相符，浏览器收到 HTTP 201。公开记录分别保留创建端点和上传端点的摘要。这个样本没有记录上传凭据有效期、签名覆盖的请求头、服务端校验和规则或实际线路上的 Content-Type。PNG 文件对象的 MIME 不能证明服务器按哪一项元数据验签。[实站标定](evidence/build59/g4-live-passive-audit.json)

自有回环服务器在读取同一份完整上传体后，分别返回 201、413 和 503。浏览器在 HTTP 拒绝时也会触发 load、loadend；必须读取响应状态并确认请求归属。客户端取消得到 abort、loadend，超时则需要受信任的 timeout、loadend。status 0 本身不能确定服务端状态。真正的 ChatGPT 前端遇到 HTTP 拒绝后是生成 Retry、显示提示、移除进度卡，还是自行创建新的请求，均需实站单独记录。[原生 HTTP 对照](evidence/build59/g4-http-control.json)

页面程序的 `sample` 和 `observe` 读取原编辑器的附件状态。`currentNamedFailure` 核对具名成员、错误文案、重试控件和上传进度。得到 START 后，`captureFailureWatch` 和 `liveOriginalFailure` 进一步核对原成员及其生命期。原卡消失时观察器已失去可归属的错误成员，无法形成 `originalCardFailed`。历史中 status 0 后得到 UNKNOWN 的产品原因可由此解释，ChatGPT 删除卡片的服务端原因无法从页面推出。

| 路线 | 已验证的依据及取得下一份证据的条件 |
| --- | --- |
| B1 · 自然过期 | 历史收据只有端点摘要，无法确定有效期。可采信正常客户端自然返回、能归属到原 PNG 的过期错误。 |
| B2 / B3 · 上传签名与请求头 | 实站正常成功样本证明服务接收了该 File。签名覆盖范围尚无供应方公开的 Temporary Chat 测试合同或授权沙箱可验证。凭据保持原样。 |
| B4 · 正常文件限制 | ChatGPT 公布每张图片上限为 20 MB。专用窗口的受控图案可生成超过此上限的单帧 PNG，实站必须独立确认系统标记、完整字节、实际输入和结果。页面提前拒绝、重编码、收到 4xx 分别记录。[官方文件上传说明](https://help.openai.com/en/articles/8555545-uploading-files-and-audio-to-chatgpt) |
| B5 · 创建请求校验 | 正常产品创建一次文件可以观察到成功或自然错误。创建请求的拒绝需独立记录；它不能证明原 PNG 的 PUT 已抵达服务器。 |
| B6 · 真实上游响应 | 已知实站归属样本为 200 创建、201 字节接收。新的 4xx 或 5xx 需要明确的上游状态与原操作归属。自有 413/503 只证明浏览器如何递交这些响应。 |
| B7 · 受控响应 | 已完成自有服务与真实浏览器的 HTTP 对照。该环境没有运行 ChatGPT 的前端。对已认证标签的任何测试必须能保持原文档和单一请求范围。 |
