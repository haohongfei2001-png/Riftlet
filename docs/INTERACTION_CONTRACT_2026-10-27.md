# Riftlet｜快速吞噬与截图生命周期：最新产品契约

**决策日期：2026-10-27（北京时间）**  
**状态：USER 已确定的交互原则；工程实现与真机验收尚未完成。**  
**优先级：** 本文与 `docs/PRODUCT.md`、`docs/DECISIONS.md` 的本日增量共同覆盖旧版“只有 verifiedReady 才允许吞噬”“UNKNOWN 必须留在可见队列”“空队列留痕迹”等规则。旧实验与历史决策保留用于追溯，不再作为新的产品验收标准。

## 1. 核心体验：迅速消失，而非等待上传成功

1. 用户按 macOS 既有方式截图；截图被收录后，一张微缩图自然从屏幕边缘裂缝冒出。
2. 用户**直接点击一次**微缩图；不要求新快捷键、弹出目标选择器、悬停展开或再次确认。先提供立即可感知、极轻的按下响应。**按住并拖动截图**仅是待评估的可选拓展，目前未批准，不能影响普通单击的响应速度或可靠性。
3. 目标是**点击时用户当前正在使用的受支持 ChatGPT 窗口/对话草稿**，不是固定目标、最近用过的聊天、任意已打开的 ChatGPT 标签或由算法猜测的目的地。Riftlet 的非激活面板不应改变目标焦点。原生端在按下时或等价的可靠点击边界冻结窗口/标签/草稿身份；随后输入前必须在目标端复核。**如果当前没有可用发言框、无法附加图片或找不到唯一有效目标，点击后截图不消失、不吞噬，也不偷偷转投后台窗口。**
4. **只要有可靠的、与本截图及原目标关联的“实际开始上传”正向证据，立即播放非常短的向裂缝内吞噬动效，并在动效中让截图彻底消失。** 不等待进度 100%、图片完全就绪、`verifiedReady`、消息发送或服务端完成。**截图进入当前草稿中的附件区域；用户直接查看草稿附件后再决定是否发送。Riftlet 不额外弹出成功 Toast、成功通知或确认。** 动效本身必须极快，不做长时间停留或循环进度演出；精确毫秒参数留给真机交互调校，不能把未批准数字写成硬约束。
5. 吞噬后立即从**可见队列**移除该截图，后续图片自然补位。原图与必要的本地私有副本/事务记录仍保留在 Riftlet 内部，以便完成核验及异常恢复。
6. **只有明确失败，或针对这张图和原操作具有极高可信度的真实失败证据时，截图才重新从裂缝中出现。** **重生后必须就是一张正常、可再次点击的截图，继续拥有普通截图的待用、点击、移除、久未使用自动归档等生命周期，不得保留不可点击的失败死卡片。** 再次上传只能由用户点击发起，不自动重传。工程应改进失败判断精度，而不是通过禁用重生截图回避误判。
7. 若结果无法判断（`UNKNOWN`），已吞噬的图**留在内部历史/待核实记录，不应自动重生、更不应永久占据裂缝**；后台继续只读核对原操作。不得把不确定冒充成功或失败；可在内部历史查看状态。对同一张图不能静默再次输入。
8. 在**不影响用户体验与稳定性**的前提下，尽量提高多图连续点击和上传发起速度，接近自然连续点击。不是为了速度无条件要求并行上传、缩短安全校验或让尚未开始上传的图虚假消失。非当前截图的未决状态不应无限期阻止**其他**截图；后台串行/并行策略以准确性、防重复及实测为准。

**“吞噬”仅描述视觉队列退出；“已开始上传”“已验证附件成功”“可以安全重试”“内部保留/归档”是不同的事实。** 禁止将视觉吞噬写成已确认成功，或反过来用严格 READY 门槛延长可见动效。

## 2. 视觉队列与裂缝

- **无可见截图时，裂缝完全不存在，连短线/缝隙都不保留。** 有截图入队时，裂缝与图片随出现动画形成。
- 可见裂缝服务于短期、直接点击的图片，而非永久待办队列；正在上传和结果未知的图片不应长期占据它。
- 未使用的截图长时间未被点击后自动归档到 Riftlet 内部；**归档期限、上限与设置界面尚未获用户确定**，不能擅自将建议的 24 小时当成正式决定。自动归档不等于删除文件。
- 支持用户移除单张可见截图和批量清空可见队列；**清空仅改变 Riftlet 可见性/内部收纳，不得擅自移除 ChatGPT 草稿里的附件**，也不等于删除 macOS 原始截图。永久删除 Riftlet 私有副本及其保留期是另一项独立操作。
- 已归档、已吞噬、结果待核实等记录通过轻量内部历史/管理入口访问。**已经进入草稿并从裂缝消失的截图，除真正判定上传失败外不自动重生；需要再次找图，用户从 macOS 原截图或 Riftlet 内部历史获取。** 不能将常驻裂缝扩大成复杂图库。
- 正常用法仍是系统截图一次＋点击缩略图一次；不得为了后端正确性强加日常确认步骤；永不自动发送聊天消息。

## 3. 最小状态／证据矩阵

| 事实 | 可见反应 | 内部记录与安全行为 |
| --- | --- | --- |
| 截图刚被收录 | 裂缝出现、缩略图从中冒出 | 保留真实来源与不可变 assetId |
| 点击已接收，但尚未确认开始上传 | 即时轻微按下反馈；**不虚假吞噬** | 冻结点击瞬间目标，持久化意图；校验无误才输入 |
| 真实附件上传已开始（正向证据） | **极快吞噬、退出可见队列** | 持久化 `uploadStarted`/隐藏事实；继续后台核对 |
| 最终成功被可靠证明 | 不再补演吞噬，也不弹成功提示 | 用户直接在 ChatGPT 草稿中查看附件并自行发送；内部记录真实完成情况 |
| 无有效发言框／附件输入能力，或上传未开始 | 截图仍在裂缝内，不播放吞噬、不消失 | 不产生外部副作用，不猜测后台聊天，不伪装已经开始上传 |
| 明确或极高可信的真实上传失败 | 截图**必须重生为普通、可再次点击**的截图 | 继续普通生命周期；用户再次点击才产生新上传 attempt；提高分类精度，不能用灰掉截图代替 |
| 超时、页面跳转、观察器丢失、网络不明等 | **已吞噬者继续隐藏在内部**；尚未证明开始者不假装开始 | 标为 UNKNOWN；不据此自动重生或自动重传；能恢复时只读核对原操作 |
| 用户自己在 ChatGPT 删除附件 | 不因“附件消失”就擅自重生 | 区分主动移除与上传失败，避免违背用户意图 |
| 待用截图久未操作 | 从可见区自动归档，最终可无裂缝 | 原始图片不因归档而被删除；保留期另定 |

## 4. “开始上传”与“极高概率失败”的验收边界

- `click`、本地 dispatch intent、浏览器执行 `change`、DOM 占位图、甚至单独出现一个删除按钮，都不必然证明目标已经**开始上传这张图**。工程必须定义可版本化的 `uploadStarted` 正向证据，绑定 asset/operation/attempt、点击瞬间目标与实际目标端流程。必要时使用目标端可观察的上传中状态或网络实际发起证据；各 surface 独立验证。它比最终 `verifiedReady` **更早**，但不是随意放松为“点了一下”。
- “极大概率失败”是用户授权的**产品方向**，不是某个未经校准的 70%/90% 数值阈值。须由相应附件的直接错误、明确拒绝、可验证的流程终止等强证据支撑，并排除已经成功附加、用户主动移除以及延迟成功等反例。单纯超时、失焦、刷新、网络中断或观察器丢失不是这种证据。
- **真正判为上传失败并重生的截图必须能够再次点击并尝试上传。** 产品不能将其展示成不可操作的卡片。工程应将**触发重生的失败证据门槛**与允许用户发起下一次 attempt 的判定校准一致；通过真实样本提高判断精度，排除仍可能完成的旧操作。证据不足则属于 UNKNOWN，隐藏在内部继续核对，而不是错误地宣布失败。现有原操作去重/防串图机制保留，但不得用禁用重生截图作为替代方案；新上传只能由用户点击触发，绝不自动重传 UNKNOWN。
- 原操作成功之后出现真实迟到失败，需要能从内部记录找到那张图并重生；但不能因为晚到的陈旧或错目标事件误召回。保留真实源图与事务证据是必要条件。
- 用户只需在正常情况下感知“点一下，图很快消失”；不要求读懂 UNKNOWN、READY、lease、receipt 等工程术语。

## 5. 对既有实现的明确影响（未实现事项）

- **模型/SQLite：** 可见性（visible/hidden/archived）不得再直接等于上传结果（prepared/started/unknown/succeeded/failed）。需要持久化并重启恢复，不得因吞噬提前写成 `used` 或直接删原图。
- **Coordinator：** 把首次真实上传开始与最终成功拆开，将已吞噬后 UNKNOWN 的后续只读核对移入后台；移除会让其他不同 asset 永久卡住的目标锁，同时避免重复上传/错误关联。
- **Web/Mac Adapter：** 为上传开始、失败、用户删除、最终成功提供各自带身份的可信观察；不把已有 `attachedCandidate` 自动升级为 `uploadStarted`。
- **AppKit：** 空队列零裂缝；新图从无到有；点击微响应；正向开始上传后极短吞噬与补位；明确/极高可信失败时逆向重生；滚动队列、焦点、按下资产身份不回归。
- **本地历史：** 待核实、已开始、已成功、归档、移除等状态有可恢复的内部记录，支持单张/批量移出可见队列和久未使用自动归档。
- **验收：** 测量点击→真实开始上传→吞噬完成的感知延迟；测试连续点击且不损失稳定性、当前发言框不存在时不消失、无成功提示、草稿中可见附件、真正失败后重生可直接再点、失败截图正常自动归档、清空队列不动 ChatGPT 草稿附件，以及慢完成/迟到失败、UNKNOWN、重启、多屏/空裂缝与系统截图。不沿用旧版“仅 READY 才吞噬”的模拟状态机冒充新规则验收通过。

## 6. 可考虑但尚未确定：按住拖动

用户提出**按住缩略图以拖动**作为可选功能。暂不视为 V1 必须实现的需求。若后续评估，应区分正常点击、按下但未移动、实际拖动，不能用“等待长按阈值”损害正常一次点击的即时性，也不能拖动时误触发上传。拖动的目的地范围、系统拖放类型、取消语义和与非激活面板的配合另行验证。

## 7. 决策范围与实施纪律

这是 **2026-10-27 最新用户决定**，覆盖旧版 P04 与旧设计稿中的 `READY → swallow`、`UNKNOWN → 留在裂缝`、`空队列仍留短线` 等规则。其余未被覆盖的决定（例如不发送消息、系统截图＋一次点击、单击资产/目标身份、保留原图、真实失败需可恢复）仍然有效。

本次只更新产品与工程说明，**不修改原生源码、不假称真实上传成功、不自动启用生产适配器、不开启发布、也不合并 main**。后续由现有工程负责人按差异实施并完成独立审查与真机验收。
