# 从个人签名过渡到 Developer ID

个人 Beta 3 的实际安装为 0.3.0 (3)。一次真实升级中，macOS 用旧版的 ad-hoc 代码要求检查维护版并返回 `-67050`。恢复旧 App 后，用户通过读取文件夹的正常面板重新选定了系统截图目录。目录书签和真实收录状态在重启后持续可用。[先前的现场记录](../../engineering/productization-20261107/closeout/permission-continuity.json)

## 准备与发行包核对

发行负责人在自己的发行环境中配置可用的 Developer ID Application 签名身份、对应团队和公证钥匙串配置文件。仓库的发行命令依次完成暂存构建、签名、提交、公证结果查询、装订和归档。对实际准备和归档的包记录源码、版本、完整清单和 SHA-256。此次 0.3.2 (5) 是隔离演练标识。正式用户安装仍由其实际 App 和构建清单识别。[发行命令与凭据参数](../RELEASE_ENGINEERING.md)

提交前，工具在临时目录用 macOS 原生解包程序还原 Apple 将收到的 ZIP，校验其中 App 的文件、目录、模式和稳定扩展属性。发布正式 ZIP 时，还须在解包副本上验证签名和已装订的票据。发行者在干净 Mac 给下载所得的实际归档做 Gatekeeper 评估，并通过 Finder 或 LaunchServices 正常启动，保留评估、首启和截图收录的分别记录。[Apple 公证说明](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

## 两次身份过渡

| 实验 | 保留和观察的事实 |
| --- | --- |
| 个人 ad-hoc 版本到首次 Developer ID 版本 | 在新用户账户中，用旧 App 和合成标记文件建立基线。记录旧 App 的指定代码要求是否匹配新 App。正常退出后只替换 App，保留数据和目录书签。在新进程内观察实际文件读取、是否弹出系统许可、是否需要用“允许访问此位置…”重新选择目录。 |
| 同一 Developer ID 团队的连续两版 | 使用两个经过真实签名、公证及装订的不同版本。重复同路径升级，在再次授权之前记录新进程的实际读取和首张收录。如果出现授权提示，记录提示的操作方、选择及新进程中的结果。 |
| 拒绝、恢复和回退 | 在隔离账户明确拒绝一次实际出现的提示，观察受保护文件读取，再用正常 App 面板恢复。更新失败时保留该时点最新数据，只换回已验证兼容的 App。比较资产 UUID、原始与私有媒体、附件操作和历史状态。 |

每个版本分别记录签名要求、书签是否解析、受保护文件是否实际读取、系统是否显示授权以及截图是否进入资产表。即便前一版的指定代码要求能验证新版，是否有权限仍以新版真实进程的读取结果为准。系统没有显示提示时，报告“未观察到提示”。[Apple 关于文件系统权限的说明](https://developer.apple.com/forums/thread/678819) · [代码要求与手动升级](MANUAL_UPDATE_AND_RECOVERY.md)

## 干净账户验证

按需运行的 GitHub macOS 作业使用新的 runner 账户。完整 App 实验按普通入口启动、导入带系统截图标记的合成 PNG、拒绝损坏包，并只替换 App 回退。另一个独立身份使用产品现有的目录书签代码和真实 LaunchServices，观察受保护目录及系统界面。附带的 JSON 分别记录可执行的行为和未能观察的路径。托管账户可能已经具有系统许可，该机器上的无提示读取不能解释为新用户授予了权限。真实 ChatGPT 双图验收需要独立、可确认的空白草稿和允许访问该 Chrome 的接口。
