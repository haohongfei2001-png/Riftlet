# Riftlet updates · 应用内更新

## 使用方法

Riftlet 1.0.0 的用户需要从官网下载 1.0.1，退出 Riftlet，然后将新版拖到原安装位置一次。从 1.0.1 起，Riftlet 默认每天检查一次更新。可以从菜单栏或设置选择「检查更新…」，阅读说明，再决定安装或稍后处理。[官网](https://riftlet.com/) · [发行说明](https://github.com/haohongfei2001-png/Riftlet/releases)

安装更新时，Riftlet 会正常退出并重新打开。安装在「应用程序」时，macOS 可能要求管理员批准。安装在个人主目录的「Applications」中，标准账户通常可以自行更新。离线时可以继续使用截图和历史功能。更新失败时，稍后重新检查，或从官网手动下载到原安装位置。保留已有截图库、文件夹授权和反馈草稿。macOS 若重新询问授权，请在 Riftlet 的权限设置中确认。[更新、备份与恢复](MANUAL_UPDATE_AND_RECOVERY.md)

## Using updates

If you use Riftlet 1.0.0, download the 1.0.1 DMG, quit Riftlet and replace the app in its existing location once. Starting with 1.0.1, Riftlet checks for updates daily by default. Open **检查更新…** (Check for Updates) in the menu bar or Settings, read the release notes, then choose to install or postpone. [Website](https://riftlet.com/) · [Release notes](https://github.com/haohongfei2001-png/Riftlet/releases)

Installation quits and relaunches the app normally. macOS may request administrator authorization for a shared Applications folder. A standard user can usually update an app installed in their own Applications folder. Screenshots and history remain available offline. If an update fails, check again later or download the official DMG and replace the app in its current location. Keep your library, bookmarks and feedback drafts. Use the permission settings if macOS requests access again. [Backup and recovery](MANUAL_UPDATE_AND_RECOVERY.md)

## Release operators

The update feed is `https://riftlet.com/updates/stable.xml`. The bootstrap feed used a signed empty channel. The first stable entry is 1.0.1 (23). The existing 1.0.0 binary continues to use its manual update path. Keep the old GitHub asset available for that version.

1. Use **Sparkle 2.10.1** on the trusted release Mac. Verify the official `Sparkle-2.10.1.tar.xz` SHA-256 `1a856d2a9edb8e628de88121d7be04cf0e2167f8641650b78fca00b14244cf27` and extract its `bin` directory. The code pins each CLI digest before invoking it. Use the dedicated Keychain account `com.riftlet.app.stable`. On the provisioned Mac, `generate_keys --account com.riftlet.app.stable -p` reads the public key already embedded in the application. Private keys remain in Keychain. Maintain a protected Keychain backup under the release owner's control. [Sparkle tools](https://github.com/sparkle-project/Sparkle/releases/tag/2.10.1) · [Signed updates](https://sparkle-project.org/documentation/publishing/)
2. Enable **immutable releases** for the repository before publishing the new stable release. GitHub applies this setting to future releases. Prepare the normal notarized universal DMG with `release-macos.py --stable`, retaining the private release workspace. Upload its verified assets while the release is a draft. Check the tag target and release notes, then publish the final, stable release under a unique `vX.Y.Z` tag. Use final bilingual notes suitable for displaying as plain text in the app. Confirm that GitHub reports `immutable: true`. [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) · [Riftlet signing and notarization](DIRECT_DOWNLOAD.md)
3. From a clean checkout based on current main, run the following command. `RIFTLET_SPARKLE_BIN` points to the trusted extracted tools and `RIFTLET_RELEASE_WORKSPACE` is the completed local release workspace. Choose an unused path for `--output`.

   ```sh
   python3 scripts/release-appcast.py prepare \
     --tools "$RIFTLET_SPARKLE_BIN" \
     --workspace "$RIFTLET_RELEASE_WORKSPACE" \
     --output /private/tmp/riftlet-new-stable.xml
   ```

   If GitHub rate-limits anonymous metadata reads, set `RIFTLET_APPCAST_GH_AUTH=1` to use a signed-in GitHub CLI for those requests. The DMG and website feed are still downloaded anonymously. The command reads the current signed website feed, verifies the public GitHub release, downloads its actual DMG and compares it with the release receipt. It checks the release tag against the accepted source, the final signed app inventory, team, Gatekeeper and both stapled tickets. Both the marketing version and the integer build must increase. The resulting feed offers the full universal DMG, on the stable channel, with its signed inline plain-text release notes. The signer uses official `generate_appcast` and `sign_update`. A second verification uses only the public key in the source Info.plist. Signing a feed or a local candidate performs no remote writes.
4. Review the generated XML against the existing feed. Propose the exact generated bytes at `updates/stable.xml` using a normal website/mainline PR. If another release changed the previous feed or the base branch, regenerate against the new version and review the result. Merge after release approval and completed CI. CI validates the signed replacement against the actual PR base or preceding main commit. It rejects removing a live item, rolling back, or replacing a version with different bytes under the same version/build. The release tag must already belong to official main, and must match the signed source except for the reviewed admission record. Keep the final tag, DMG and feed receipts. Never edit or reformat the signed XML in the publishing pipeline.
5. After Pages deploys, fetch the live feed and compare the exact bytes. Check the update inside an isolated installation one version behind, confirm user consent, relaunch and inspect its preserved library.

   ```sh
   curl --fail --silent --show-error https://riftlet.com/updates/stable.xml -o /private/tmp/riftlet-live-stable.xml
   cmp /private/tmp/riftlet-new-stable.xml /private/tmp/riftlet-live-stable.xml
   xcrun swift scripts/verify-update-signature.swift Resources/Info.plist /private/tmp/riftlet-live-stable.xml
   ```

If a release fails, preserve the current library and ship a corrected, higher version and build. Replacing a database with an older backup can discard intervening history. An interrupted public download, a tag/source mismatch or an unverified distribution receipt stops feed generation before a new entry is released.

The committed initial feed was created with `python3 scripts/release-appcast.py bootstrap --tools "$RIFTLET_SPARKLE_BIN" --output updates/stable.xml` using the provisioned signing Mac. This one-time command requires an unused feed path and an existing Keychain public key matching the app. Exercise test releases using a separate app, isolated feed and ephemeral test identity.

## Verification

`python3 scripts/test-release-appcast.py` checks the repository feed using the application public key, rejects changed content and incorrect keys, and exercises release selection, increasing versions, source provenance, signed item policy and collision-safe output. On the isolated signing/test Mac set `RIFTLET_SPARKLE_TEST_BIN` to the official tools directory before running this command to include a generated QA DMG. That case signs a temporary feed and archive with a disposable in-memory test key, checks both with Sparkle and CryptoKit, and rejects tampered, incomplete and incorrectly signed downloads. Actual application restart and data continuity are covered by separate installation tests.
