# Riftlet｜消费者版本收口裁决（2026-11-10）

> **状态：用户最新明确产品决定，优先于 2026-11-07 之前的五形态探索及旧托盘宽度结论。** 本文在 PR #57 签名候选 `0.3.4 (13)` 的**独立后继分支**记录。仅记录并约束下一轮实施，**不冒充已实施原生代码、已获得用户视觉批准或已通过本轮 CI**。
>
> 目标不是再加功能：**删掉冗余形态、统一整个原生产品的设计、统一安装身份与发行版本，让 Riftlet 真正成为普通人每天愿意使用的软件。**

## 1. 只保留三个桌面呈放形式

正式形态**仅三种**，按产品呈现/选择顺序：

1. **截图托盘（Tray）**：直接呈放截图；固定窄幅，两列×最多两行；截图入口作为队列末项；完整四键独占一行；保留已验收的状态路径、顺序与吞噬逻辑。
2. **风铃（Wind Chime）**：本合同建立时，原生入口尚未启用。11 月 11 日已找回 10 月 31 日的 R1、R2 原始设计往返及用户提供的参考图，并将风铃接入正式 App 的队列、设置和首用引导。[历史设计裁决](https://github.com/haohongfei2001-png/Riftlet/pull/58#issuecomment-6770640988)
3. **微缝（Micro Slit）**：保留既有轻量形态与其已确认的点击、遮挡、磁力/无动效等行为。

**删除产品范围：折页 Edgefolio、口袋 Pocket。** 从真实用户可见的形态枚举/设置/首用/说明/截图/预览/默认模式及生产代码中移除；如有专门为这两者存在的代码、资源和测试，则在确认无共享用途后清理。Git 历史和已有审查证据保留以便追溯；不重新合并旧的 PR #52 作为产品功能。

**数据兼容：** 对旧候选曾保存的 `edgefolio` / `pocket` 偏好，读取时安全映射到保留的受支持形式（建议托盘），不得因删除枚举导致 JSON 解码失败、启动崩溃或修改截图数据；不重置用户存量的收录目录、截图、操作、UNKNOWN、START。

**新用户默认：** 将托盘作为优先展示的主形态候选；最终默认配置在三形态实际原生验收时落定，**不得静默覆盖现有用户的微缝选择**。

## 2. 托盘宽度：约为实际显示器宽度八分之一

**2026-11-10 用户最新决定为权威。** 以承载托盘的**目标显示器**完整逻辑点宽度为基准：

```swift
targetTrayWidthInPoints = targetDisplay.frame.width / 8   // ≈ 12.5%
```

- 旧实现 `display.width * 246 / 1672` ≈ **14.71%**；与用户新决定不符。必须废弃作为**屏宽占比**的公式。
- 例如 1920pt 宽显示器，目标托盘约 **240pt**，不是旧的约 **282–283pt**。像素对齐允许半点/一点误差；极窄屏才作必要的安全裁切/缩放，不能普遍以“最小宽度”把比例撑回 14–15%。
- **参考 PNG 保留为材质、边距、截图槽位、圆角、行距、动效和高度相对比例的视觉依据**；对从 246px 母版归一化得到的内部度量进行等比例缩放。不要按比例缩窄后又补回不成比例的按钮或阴影。
- 仍然固定宽度，两列×最多两行；0–1 张在正常折叠时仅一行；两条单图展开路径、三图 B/C 补位、裁切、滚轮、点击目标、缩略图 Fit 均保持。所有四键必须留在托盘内部，不能为了四键增加宽度。
- 应在不同显示器、左右边缘、不同 backing scale 下检查实际宽度占比与触控命中区，并用真实 WindowServer 帧确认。Saytile 是视觉同宽参照而**不是 Riftlet 的布局运行时依赖**。

## 3. 不是只修托盘：重设计完整的消费者原生 UI

目前 `RiftSettingsCenterPages.swift` 仍用六个旧式模块、多个工程数值字段与逐项大卡片：`firstCenterFromTop`、`minimumHitWidth`、`numberGap`、`rowPitch` 等。用户已明确指出**“整个设计没有达成，设置等界面还停留在旧版本”**。不能把现有设置页的配色改成淡紫色就当作重设计完成。

### 设计范围（必须同一轮连贯审查）

- **桌面主体：** 三种保留形态、收起/展开、位置、指针命中、与原生桌面交互；托盘沿用已确认的浅白紫蓝玻璃母版，但宽度按本裁决变更。
- **设置中心：** 整体信息架构、导航、侧栏、控制行、预览、保存反馈与错误恢复；用简洁的 macOS 原生语言重新组织，而不是把旧控件逐一加描边。外观统一、内在逻辑精简。
- **首用与权限：** 首次启动、系统截图来源、Chrome 自动化/脚本授权、屏幕录制与恢复。只在确实需要的时刻解释权限与失败，不堆满技术解释。
- **历史、存储与恢复：** 与新设置及桌面使用统一视觉；继续保持已有历史双样式和 UNKNOWN 安全边界，不将历史降级为仅展示卡片。
- **菜单栏/状态与反馈：** 与新设置统一术语、图标、信息密度和状态语言；不添加与功能无关的 Logo、标题、浮动工具栏或营销文案。

### 对普通用户只呈现必要选项

建议设置中心用清晰且少量的顶层分区（具体排布由真实原生设计评审定稿）：
1. **外观与布局：** 三形态可辨别的真实小预览、目标显示器/边缘位置、与该形态有关的选项；托盘颜色与强度、遮挡、可见张数，只在托盘选中时出现。
2. **截图：** 使用系统截图/内置入口、截图目录、默认方式与常用方式；每项控制的描述应对应真实能力。
3. **使用与历史：** 启停收录、登录启动、历史浏览、备份/恢复、存储和未确认结果。
4. **权限与帮助：** 对应实际系统授权的状态、仅需一次的恢复动作、版本与可选诊断。

将不影响普通用户日常选择的调试/几何参数放到真正独立的“高级”折叠区，或移出面向消费者的设置；保留有用能力、默认值、无障碍与配置兼容，不要删功能代替重设计。

### 视觉方向与验收

- 参考用户一贯选定的轻量、精致、克制 macOS 原生设计：高质量白色半透明材料、自然留白、严谨信息层级和细腻状态变化。**视觉一致性依赖实际窗口截图，而非生成的 AI 卡片或只有 HTML 的原型。**
- 优先减少页面密度和重复选项；每条文案须有实际信息价值。不要把产品做成配置工程控制台。
- 需交付真实 macOS 设置窗口的所有主页面、状态栏/首次引导/历史关键画面，进行用户视觉裁决。动态效果、缩放、Light/Dark、减少动态/提高对比度、键盘/VoiceOver 都不因新外观失效。
- **先提出一份统一设计的原生审查候选，再把视觉规范变成代码；不能只实现托盘继续保留旧设置中心。**

## 4. 版本与旧安装包整理：唯一候选，保留数据

用户决定：**不在桌面与下载目录保留多代可执行安装包、反复出现 0.2 / 0.3.3 / 0.3.4 多个容易混淆的入口。**

- **保留一份明确身份的最新待验收签名候选**（当前为 `0.3.4 (13)`），后续新设计完成时再替换为新的更高 build。每个安装包明确 version/build、HEAD/source SHA、签名 Team、文件摘要；旧报告只作为不可执行证据保留。
- **正式安装与新候选必须区分**：当前正式个人安装仍为 Personal Beta 3 `0.3.0 (3)`，已经在真实生产数据上运行。**在新版本完成端到端附件、升级身份/截图目录权限连续性和数据完整性验证前，不得为了“只留最新版”直接删掉唯一可用正式 App**。
- 对已确认淘汰的 ZIP、DMG、旧版演示 App 进行**逐项有记录的可逆清理到 macOS 废纸篓**；不删除真实截图来源、用户数据目录、媒体、操作/START/UNKNOWN、备份、签名材料、Git 历史或审查录像。避免使用广泛匹配的 `rm -rf *riftlet*`。
- 待新版被**正式批准且安全升级完成**，确保 Applications 中只留一个正式 Riftlet.app、主要下载位置仅留当前正式发行包。旧活动版本可在安全回退边界过后完成最终整理；不额外保留一堆旧候选。
- **不能把“最新签名候选”谎称“最新已正式安装版本”**；版本更新、代码合并、下载发布是三个不同动作。

## 5. 正确的后续实施与验收顺序

1. **裁剪范围和数据兼容**：删除 Edgefolio/Pocket，确定三形态呈放/选择机制；风铃如无足够的用户原始设计证据，标记真实缺口，不能编造成已交付。
2. **统一原生视觉设计**：先构建整个产品的设置/首用/历史/状态栏/三形态真实原生统一候选，取得用户外观判断，然后实装；不再循环一张张粗糙概念效果图。
3. **托盘宽度改 1/8**：作为上述视觉布局的一项正式任务；量化多个尺寸的真实 WindowServer 几何，全面回归两行、四键和命中，原 0.3.4(13) 的 14.7% 数据是**旧版验收基线**而非新尺寸 PASS。
4. **签名新候选与验证**：完整功能+设置持久化、跨版本存量配置读取、原截图与日志完整；恢复可授权 Chrome 草稿时完成真实双图附加。浏览器不可访问时保持 NOT_RUN，不伪造成功。
5. **用户批准后标准合并/升级**：按 G/H、正式 CI 和可回退升级流程执行。先本机最新版本，再启动可信分发与真实封闭 Beta；未完成前 PR 仍保留 Draft。
