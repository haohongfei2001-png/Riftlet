# 数据与隐私

Riftlet 在本机收录截图文件并保存私有副本，记录队列、历史及附加操作状态。点击附加时，图片进入你选择的当前受支持聊天；之后由聊天服务处理。Riftlet 不替你发送消息，不提供云端截图图库、OCR 或跨设备同步。

## 本地保存

普通入口的数据目录是 `~/Library/Application Support/Riftlet/`。截图原件仍在 macOS 的保存位置；私有副本、SQLite 队列、导入 journal、暂存文件和偏好各有用途。反馈使用独立的 `Feedback-v01` 数据库；部分首次引导/目录访问凭据在系统偏好中，反馈能力凭据在钥匙串中。仅备份数据目录不等于备份全部系统授权或钥匙串。

| 状态或动作 | 保存含义 |
|---|---|
| 待附加/可见 | 图片可从边缘操作；原图与私有副本保留 |
| 开始上传后收起 | 对应接收开始已被观察到；不等于网络上传完成 |
| 已附加/已使用 | 本地记录对应的完成证据；不是删除原图 |
| 待核实（UNKNOWN） | 结果无法确认，保留记录并避免自动重传；不把它改写为失败来重新发送 |
| 归档或从队列移除 | 改变本地可见性；保留历史和文件，不删除远端附件 |
| 用量检查 | 有界、按需的逻辑字节统计，可能不完整；不是可释放空间或 APFS 实际占用承诺 |

当前没有自动删除私有历史的保留期限。截图使用增长会增加磁盘占用；磁盘不足会阻止无法安全保存的新收录并提示，不能用删除旧 UNKNOWN 或媒体作为自动恢复方式。保留天数、配额与永久删除交互尚待产品决定。

## 更新检查

1.0.1 默认每天从 riftlet.com 读取更新信息。用户选择下载时会连接 GitHub 的发行文件服务。打开「设置 → 权限与帮助 → 关于与诊断」可关闭「每天检查更新」。[更新访问与数据说明](consumer/PRIVACY.md)

## 反馈与诊断

“反馈与建议…”只在你明确发送后产生该条反馈的网络发送权限；关闭窗口不发送。反馈正文、报告标识、版本、创建时间，以及你选择附带的诊断会发送到反馈服务。正文由你输入，请避免写入密码、私人聊天或敏感截图内容。

新反馈草稿的可选诊断默认不勾选，并可预览；同一未发送草稿重新打开时，保留此前的选择。代码限定为少量事件类别和计数，例如收录/权限/队列状态；不包含截图字节、截图路径/标识/哈希、剪贴板、浏览器会话或聊天正文。发送失败的已授权反馈可能在本地等待重试；不能把“排队”称为已送达。反馈通道与截图输入独立。删除反馈与卸载本地 App 是不同操作，不应承诺卸载会删除已提交的服务端反馈。

本仓库及公开问题区不能接收私人截图、原始生产数据库、浏览器 profile、诊断 traces 或密钥。反馈服务的运营留存、外部隐私声明与公开发行负责人尚需最终确认；本文件说明当前技术行为，不虚构法律承诺。

## 备份

使用[存储恢复工具](STORAGE_RECOVERY.md)生成可校验的离线副本。工具保留历史、UNKNOWN、媒体和未完成导入文件；不自动修复、清理或打开真实聊天。备份含私人图片和反馈，应保存在你控制的位置。恢复先验证并写入新的空目录；原目录保留供回退。

## 单张永久删除的设计提案

当前版本没有永久删除截图副本的功能。建议首版仅允许用户主动删除**已归档、从未发起附加的一张系统截图的私有媒体**。从边缘收起、清空可见队列、自动归档、磁盘不足、退出和卸载都不触发删除。此设计待独立准入。

### 用户意图与文件范围

从历史详情单独选择「删除此私有副本…」。确认页显示所选缩略图、截图时间、将处理的本地文件逻辑大小，以及是否知道系统原图的位置。明确告知“将永久删除此私有副本。系统原图、聊天附件和已有备份将保留”。默认焦点为「取消」，关闭与 Escape 均取消。只有单独点「永久删除此副本」才记录一次请求。切换记录、筛选或分页不能把原确认转给另一张图。

打开确认页时即固定数据根、资产 UUID、可见性修订，以及每个私有文件和父目录的文件系统身份。点确认时重新核对这份清单、独占引用和完整操作历史；此时不能把同名替换物重新登记为用户刚看到的对象。资产正在被使用、曾有任何附加操作、有 UNKNOWN、导入尚未提交、引用不全或身份变化时，保留文件并说明原因。正常已提交的收录日志可以用于核对归属，不应与未完成导入混为一谈。

仅列入能够证明归属的单张私有媒体，以及确实存在且独占的私有预览。目录外路径、系统原图、内置截图及编辑原件、其他资产、反馈和备份均不在授权清单内。不按文件名、相同像素或哈希选择另一份文件。发现共享引用、符号链接、硬链接、目录身份变化或不明确的历史记录时停止该请求。逻辑大小只用于说明影响范围。

### 中断和冲突怎样处理

| 拟议的持久边界 | 重新打开后执行的检查 |
| --- | --- |
| 确认前 | 取消不写删除意图，也不移动文件。两次点确认最多创建一份绑定原资产与修订的请求。 |
| 已提交意图 | 在队列事务中重查资格，记录请求 ID、资产、来源标识和明确的私有文件清单。将该资产保留给本请求，新附加、恢复到边缘与常规导入恢复都要识别这一保留。若有其他操作先取得资产，删除不生效。不同截图可正常使用。 |
| 已隔离待清理 | 从第一次移动起就要能绑定获准的原对象，或证明该动作全程使用排他的命名空间。SQLite 事务只保护账本；无覆盖改名只保护目的名，不能证明搬走的是刚检查过的源文件。不能证明时，原地停止。获准移动后在同一卷隔离，同步相关目录并持久记录逐文件结果。若在移动与记账之间中断，重开要核对原名、隔离名和已登记身份；两处并存、都为空或证据矛盾时保全现场。单处匹配也不是已清理的证据。特殊文件应拒绝；检查 FIFO 等对象不能一直阻塞数据根。 |
| 已标记、清理中 | 主媒体和预览分别记账，区分“仍在原位置”“已隔离”“已获准清理”“已核实清理”和“去向待核对”。在普通收录日志恢复前先应用本请求的标记。最终清理仍须绑定原对象并同步父目录。仅凭名称、散列、合作进程锁或重复检查不能移除同名替换物。两个获准位置都为空，可能是外部改名；不追删其他路径，也不由缺失推断是本请求所删。 |
| 已完成 | 所有获准项都有一致、可核实的完成证据，且不再残留对应隔离文件，才显示“本地副本已删除”。单独的完成行或清理授权不是结果。出现矛盾则保留现场。仅保留抑制原截图再次收录所需的来源身份和必要记录，不写原图或联系聊天服务。 |

重启应先核对已登记的请求，再启动常规导入恢复和目录收录。每次移动或清理前都须复核同一资产的引用和操作历史。新附加、UNKNOWN、未决导入或身份冲突出现时停止并保全余项。例如预览仍在、主媒体在已登记位置不可见时，应分别说明“预览已保留；主媒体去向待核对”，不能把整张标为“已删除”或“均可恢复”。请求开始前空间不足可拒绝，开始后空间不足必须能说明停在哪一步。

同一个 APFS 卷在重启后可能得到新的挂载设备号（`st_dev`）。如果已确认的删除请求与重启后的文件身份不完全吻合，即使卷 UUID、inode、出生时间及内容摘要仍相同，该项也显示“去向待核对”。保留原请求、原账本和文件，禁止自动改写身份或继续移动、清理。

### 旧版本、备份与重导入

Personal Beta 3 接受至 v3。新版[普通截图队列](../Sources/RiftletCore/SQLiteDatabase.swift)使用 v4。[原生恢复](../Sources/RiftletCapture/PrivateAssetImporter.swift)会重新检查 journal、media 和 staging。[队列](../Sources/RiftletCore/QueueStore.swift)按来源标识去重。Beta 3 历史记录的[来源标识](../Sources/RiftletCapture/FileValidation.swift)只有设备号、inode 和出生时间，缺少原卷 UUID。拟议的删除标记须保留原始来源身份，并在改名、重扫、卷重新挂载及旧日志恢复时生效。证据不足时，单独保全可能属于同一原文件的候选。能证明是另一来源的独立截图，即使字节相同，也照常收录。

普通截图库 v4 用于保护卷来源标识。今后引入删除语义时，需要能让现有 v4 读取器也拒绝的新版本边界。只在 v3 下增加一个旧客户端不读的字段或表不足以保护数据。回退前先备份最新状态，在独立副本上验证旧版拒绝不兼容的数据、保留原行和媒体，并且未进入导入恢复。以兼容版本继续使用当前历史；恢复删除前备份应是用户另行选择的恢复动作。不得为了运行旧 App 将旧数据库覆写到现用历史。

[离线备份工具](STORAGE_RECOVERY.md)现会把缺失的引用媒体报告为需检查。删除功能准入前，须让备份检查、核验、恢复都能识别同一资产的精确完成标记，仍报告其他意外缺失。备份有未完成意图或隔离文件时应明确说明仍可能包含私有图片。恢复仅写入新的空目录，删除前备份会带回当时的副本。此动作不承诺擦除 APFS 快照、系统备份或聊天服务中的图片。

恢复到新目录会产生新的文件系统身份。同名同字节的恢复文件不能继承旧账本的移动或清理授权；恢复后冻结这些请求，先核对现场。备份可以同时“字节核验通过”和“资料状态需关注”。即使一张图片的缺失有完成证据，另一张未登记的缺失仍须单独提示。

### 已观察的兼容行为与放行条件

在 PR #50 的 `1b209dd` 上，用新的模拟数据根和一张合成 PNG 运行了实际的原生收录器与队列。为 v3 加入测试专用标记表后，旧逻辑仍根据合法 journal 将 staging 中的同一 PNG 移回 media，原归档资产仍在。原文件改名后仍得到同一 UUID，字节相同的新文件得到独立 UUID。另一个仅将存储版本标为 4 的合成副本被当时只支持到 v3 的队列以“不支持的 schema”拒绝，原资产行保持一致。这些观察没有执行永久删除或使用正式安装。

同一源码的离线工具对删除前的合成数据完成了备份、核验和异地恢复，三步均退出 0，PNG 可找回。另一个样本仅把该份私有文件移到隔离目录并加入测试标记表，三步均退出 2 并保留 `missing-media`，备份字节仍能核验。系统原图样本、收录日志和序号 1、8、14 的三条 UNKNOWN 完整记录保留。两组实验说明现有读取器需要适配未来的删除语义。

提案返回独立设计审查时，应交付以下隔离验收。所有用例均需核对系统原图、其他私有媒体、所有历史 UNKNOWN、反馈和既有备份，并检查没有浏览器输入。

在 `15b73982` 的四组隔离样本中，现有工具对删除前快照的备份、核验、恢复均退出 0；处理中、仅登记目标缺失、另有意外缺失均退出 2，但备份字节和 UNKNOWN 全行均保留。后两组分别报告两处和四处缺失（资产及对应日志）。另一项实测中，原 Beta 3 读取器在缺少格式门槛时将缺失资产改记为 `missing`，有效日志和暂存文件还能重建私有副本。这些是现有读取器与模拟账本的结果，没有启用删除。

- 在确认框取消、切换到别的记录、连续确认，以及归档状态变化后提交。只有仍匹配的原资产可能产生一个请求。
- 在附加保留与删除意图的两种先后顺序、同名替换、共享引用、符号/硬链接及磁盘满时重放。所有拒绝均要保留文件、原操作和可解释状态。
- 在意图提交、重命名、目录同步、标记提交、逐项清理和最终状态写入前后逐一中断并重启。只继续已核实的原请求，状态不确定时保留现场。
- 模拟账本已在真实 macOS 客体内经过进程中断、正常重启与两次虚拟机强停。正常重启的样本保留了原请求、UNKNOWN 和隔离文件。两次虚拟机强停后，重新挂载的设备号变化，核验均冻结请求并保留了原图和备份。物理存储断电仍待验证。
- 使用隔离研究原型，分别记录进程中断、系统重启、虚拟机非正常停机、物理存储断电及独立备份恢复的结果。只有真实物理断电能满足掉电项。上述必需的中断、重启、断电及备份恢复通过，并经过产品设计和独立数据恢复审查前，不进入生产实现。
- 重扫同一文件、改名，再引入一张相同内容的新截图。核对旧图不复活、新图仍可收录，历史里的已删除状态不会触发上传或恢复。
- 针对删除前、处理中、完成后的备份分别做校验及新目录恢复，再用隔离的旧版与删除感知版本分别打开。预期删除与真实缺失必须能区分，不能仅凭退出码或 schema 号放行。
