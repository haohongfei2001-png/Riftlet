# Riftlet cloud QA: keep three evidence lanes separate

1. **Hermetic macOS regression.** On the exact new head inspect the changed paths first. Reuse [Native foundation](https://github.com/haohongfei2001-png/Riftlet/actions/workflows/native-foundation.yml) (arm64 and Intel); verify source admission on the actual merge candidate and do not rerun already successful unchanged jobs. Swift/AppKit, native screenshot and synthetic DOM/Chrome replays are not signed live-site tests. When the adapter changes, run the affected controlled cases as applicable via `node Tests/ConversationProviders/run.cjs chrome` and `… edge`; these use a disposable Chromium process and mock drafts. When time-line/drag behavior changes, use the dedicated unlocked Mac fixture `bash Tests/NativeTimeline/run-drag.sh`; the local AppKit receiver is not a website. Existing goldens must retain their own candidate SHA and scope.
2. **Signed install/upgrade.** Reuse the owner-gated [hosted-Mac release identity workflow on its validated QA branch](https://github.com/haohongfei2001-png/Riftlet/blob/ce4bc1c0b9900f75c1334227744a33bbfbf77e6d/.github/workflows/release-identity-host.yml), with an explicitly hash-pinned owner-staged artifact. No stable feed change, no private DMG in workflow artifacts, no release promotion. New signed hashes or updater/SQLite changes merit re-running only their affected gate. Compare upgraded real executable hash, CodeDirectories, tickets, SQLite originals, history, and preferences. The archived 65→68 test is not a 67→68 test. Use the optional read-only audit script for raw downloaded ZIPs:
   ```sh
   python3 scripts/verify-cloud-upgrade-receipt.py --artifact hosted-receipt.zip \
     --signed docs/releases/1.1.0/evidence/signed-candidate.json \
     --formal docs/releases/1.1.0/evidence/formal-checks.json \
     --summary docs/releases/1.1.0/evidence/upgrade65to68-private.json
   ```
   The three build 68 record files are on the [pinned acceptance evidence branch commit](https://github.com/haohongfei2001-png/Riftlet/tree/ad837a3801049d0798b7c46e55433b6e809bdace/docs/releases/1.1.0/evidence), not necessarily on main. Download them and the ZIP from the exact [successful run](https://github.com/haohongfei2001-png/Riftlet/actions/runs/45634687649) before running the script. The script checks receipt agreement only. It does not mount a DMG or rerun an upgrade.
3. **Signed browser end-to-end.** The signed Riftlet and ordinary target browser must execute in the same macOS desktop with an authorized, dedicated browser profile. A Linux cloud-browser login is only useful for that browser's web-surface lane, not authorization on the Mac. In a dedicated unsent test draft, record browser version, macOS build, candidate DMG hash and site, then measure explicit click with one input/one matching card, two distinct attachments with draft text and prior attachment preserved, historic original click, native drag accept and Esc cancel, and zero sends/submit. Separately mark if page event counters cannot be observed. Do not record uploaded test content in a public artifact, IDs from real conversations, cookies, sessions, passwords, or screenshots containing personal data. Use synthetic image assets. On auth or platform denial, record `NOT_RUN` and reason. Use `PARTIAL` when an actual site/browser demonstrated some native paths and others lack evidence; `FAIL` requires an actual executed attempted path with observed wrong behavior. Never promote browser-only preflight into native matrix. For this pass, use only guest-mode live preflight, do not ask for logins, and leave any authenticated rows unrun; previous signed authenticated results remain historical evidence. If a later pass is separately authorized for dedicated authenticated profiles, prioritize missing ChatGPT Safari click, then Claude/Gemini, then the rest in small batches. Known ChatGPT Chrome/Edge evidence is carried forward only for unchanged relevant code and identified version; do not turn 57 combinations into a blanket release gate.

Hosted jobs are fresh VMs. If approved later, an independent persistent Mac should use an isolated macOS user and dedicated browser profiles, download explicit hash-verified candidates, accept only trusted jobs, and export only sanitized results. Do not attach it as a persistent self-hosted runner to the public PR repository.
