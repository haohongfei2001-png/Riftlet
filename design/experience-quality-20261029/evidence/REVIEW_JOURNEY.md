## 2. 交付前必修

### R1 · 反馈记录的存在和状态不能由折叠开关决定

**范围：Q07，原型交付前必修；新增原生工程仍按 Q07 的 P1 及集成等待条件执行。**

证据位置：HTML `initialize` 第 46 行、`feedbackRecord` 第 63 行、`renderFeedback` 第 64 行、`toggleRecords` / `confirmDelete` 第 67 行。

| 操作 | 当前可复现结果 | 为什么必须修正 |
| --- | --- | --- |
| 反馈／服务未配置，初始“本机反馈记录 · 0” → 展开 | 变成“本机反馈记录 · 1”，出现从未创建的记录 | 将阅读行为呈现成记录创建行为。 |
| 反馈／待发送，本有一条记录 → 折叠 | 记录数变为 0 | 用户无法判断记录是否仍保留。 |
| 待发送 → 取消待发送 → 确认 → 再展开 | 同一示例再次显示“仅保存在本机／取消待发送” | 已明确取消后又回到可取消的待发送状态，违背“保留记录、取消投递”的语义。 |

**最小修正：** 在 mock 中独立保留 `records`（或固定的 `recordState`）与 `recordOpen`。计数只来自记录集合，展开只控制可见性。单条确认时冻结记录 ID；从 `queued` 且明确从未尝试提交的记录迁移到 `cancelled`，保留一条记录，呈现“已取消本机投递（未发送）”，不再提供“取消待发送”。原型可以只读呈现该结果，无须补做新的正文清理功能。远端结果待确认仍只可申请删除；确认申请后保留编号与记录并显示“等待删除确认”，不得立即称“已删除”。

**验收：** 无记录展开/折叠始终为 0；有记录展开/折叠始终为 1；取消后切换折叠至少两次，状态和计数保持；`remote → deleting` 的记录不变成 cancelled；以上操作不改变截图、UNKNOWN 或历史集合。

### R2 · 空白与保存失败不能进入“已保存待发送”

**范围：Q07／Q08，原型交付前必修；新增原生工程仍按相关 P1 与既有安全守卫执行。**

证据位置：HTML `renderFeedback` 第 64 行、`bindProduct` 第 65 行、`submitFeedback` / `tryClose` / `retrySave` 第 67 行。原生正文门槛固定证据：[FeedbackModels.swift，443d21da，第 67–68 行](https://github.com/haohongfei2001-png/Riftlet/blob/443d21da1a55c0061eafced823b5406879b96024/Sources/RiftletFeedback/FeedbackModels.swift#L67-L68)。

| 操作 | 当前可复现结果 | 应有行为 |
| --- | --- | --- |
| 将正文改为三个空格 → 保存待发送 | `localQueued=true`，显示“已保存待发送” | 保留编辑；不创建记录，提示“请先写下反馈”。主动作不可用，动作入口也检查去空白正文。 |
| 保存失败情境 → 保存待发送 | 明知 `feedbackSaved=false`，仍显示“已保存待发送” | 在本地持久化成功事实前保持失败；不新增记录，不宣称保存。 |
| 接着点击保存并关闭 | 又显示“草稿还未保存，文字仍在这里” | 提交与关闭使用同一保存状态，不能对同一份正文互相矛盾。 |
| 保存失败情境中继续输入 | `bindProduct` 直接设置 `feedbackSaved=true`，底部改成“草稿已保存在本机” | 编辑只改变正文/revision；当前模拟失败条件未解除时，不能由输入事件产生保存成功事实。 |

**最小修正：** 使用独立的草稿保存状态（例如 dirty／saving／saved／failed），主按钮和动作守卫共用同一条件：非空白、限额内、无 marked text，并取得该 revision 的本地保存成功结果。这个原型可继续由显式“重试保存”模拟成功；失败期间“保存待发送”禁用或说明先重试，调用钩子也不得绕过。输入可以保留文字并标记待保存，不自动解除失败情境。关闭失败保留窗口、文字、记录及“重试保存／复制正文”；成功后的关闭仍只保存，不投递。

**验收：** 空字符串、空格、换行均不能 enqueue；失败时提交、编辑后提交、连续关闭均不产生“已保存”结果或新增记录；显式重试成功后才允许本地待发送。`nil endpoint` 下所有这些路径仍显示“当前不会上传／开发者尚未收到”，不能模拟收件回执。当前 scalar 与 UTF-8 限额实现保留。

### R3 · 历史列表、详情、完整预览和筛选必须绑定同一条记录

**范围：Q06，原型交付前必修；新增原生工程仍按 Q06 的 P1 执行。**

证据位置：HTML `renderHistory` 第 61 行。当前逻辑把 `scenario==='preinput'` 应用于所有选中条目，详情元数据固定；完整预览调用 `sample()`，未传递选择身份。

| 操作 | 当前可复现结果 | 为什么必须修正 |
| --- | --- | --- |
| “输入前取消”情境 → 选择第二条“已附加” | 标题是“已附加”，正文却说“本次在输入前取消，没有进行附加” | 核心结果互相矛盾。 |
| 同情境 → 选择第三条“已归档” | 详情标题/正文仍套用取消情境 | 误导记录是否曾附加及为什么可恢复。 |
| 选择第二或第三条 | 列表时间不同，详情仍固定今天 09:38 | 用户不能确认自己查看的是哪一张截图。 |
| 选择第三条 → 完整预览 | 详情用 `sample(2)`，大预览用默认 `sample(0)` | 预览换成另一张图；可能误导用户对“放回裂缝”的对象理解。 |
| “结果待核实”情境 | 侧栏选择“待核实”，列表仍同时出现“已附加／已归档” | 原型把筛选与真实状态分类混淆。 |

**最小修正：** 定义三条稳定的 mock 记录，每条有 ID、时间、图片标识、结果状态和 Core 可恢复资格的只读示例值。列表、详情、预览与按钮全部消费当前 `selectedID`；输入前取消只替换对应第一条记录的事实，不能覆盖其他记录。进入“待核实”筛选只显示该状态；若希望同时比较三种状态，应选“全部”。筛选后如原选择不再可见，选择第一条可见记录或显示无选择详情，不能保留不匹配的动作。

**验收：** 三条记录逐一选中再打开预览，图片、时间和状态一致；已附加记录不会显示取消正文或“放回裂缝”；UNKNOWN 从列表、详情、预览及测试钩子均无恢复动作；输入前取消的记录可呈现一次新的手动动作资格，但不能自动附加；无可见记录时没有预览或恢复对象。

## 4. 不阻断本次设计，但需如实保留的验收边界

原型 sheet 声明 `role="dialog" aria-modal="true"`，目前只显式设置首次焦点与 Escape 行为；没有看到背景 `inert`、完整 Tab 焦点循环和关闭后焦点回到原触发按钮的逻辑。真实浏览器键盘遍历尚未执行。因此这不是已经复现的焦点越界缺陷，但不能宣称键盘/辅助功能验收通过。若交付声明原型具备完整键盘可用性，应补浏览器验证并按结果修正；原生实施必须沿用 `NSAlert.beginSheetModal(for:)` 与 AppKit 标准焦点行为。

原型目前演示 IME 和保存失败关闭，未完整演示本地保存 busy、编辑尚未加载等所有 Q08 门槛。这些状态已在实施规格定义，应保留为工程验收项，不能把缺少交互场景推断为原生缺陷。首用的系统授权、屏幕/Spaces、实际像素清晰度、VoiceOver 和重新启动恢复同样没有在此原型中被证明。
