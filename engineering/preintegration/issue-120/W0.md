```sh
python3 -B engineering/preintegration/issue-120/baseline.py --workspace "$RIFTLET_RC_WORKSPACE"
python3 -B -m unittest discover -s engineering/preintegration/issue-120/tests -v
```

## 证据与审核顺序

1. 在 1.0.7 的同一签名候选上采集 G1 至 G6，先检查 G1、G2 的实际登录草稿和 G4 的原卡失败恢复，再决定 #119 是否可合并。每个事件保留原始测量，含未通过、额外点击和未知结果。原始数据留在私有发行空间。App 身份使用发行工具 inventory(Riftlet.app) 的规范 JSON SHA-256，键为 App 内相对路径，包含文件内容散列、权限、符号链接和相关扩展属性。DMG 使用原文件的 SHA-256。
2. 每个 gate 分别保存产品记录及独立观察记录。公开的去隐私投影位于 `docs/releases/1.0.7/evidence/acceptance/Gn.run.json` 与 `Gn.observer.json`。两份各自标注 kind、collector、gate、candidate、sessionID、status、artifactSHA256 和 measurements。每条按 sampleID 与 case 对照，浏览器场景还对照浏览器、原操作和目标；输入来自原生记录，原稿中新卡、载荷和零发送来自观察者。原始材料按实际字节摘要保存在私有 workspace 的 `acceptance/w0-originals/<sha256>`。签发前非作者要查清采集来源、独立性、完整性及投影是否符合原件。结构验证不能替人证明现场真实。
3. 机器记录的 gates 列出每份投影的 commit、path、sha256、artifactSHA256 与实际状态。将 candidate、pr119Head 和 gates 三字段组成对象，按 UTF-8、键名排序、紧凑分隔符的 JSON 计算 SHA-256。非作者在项目既有独立源码审核报告内以 `acceptance107IndexSHA256` 绑定该值。证据可在二进制冻结后归档。审核后依既有流程产生只修改 source-admission.json 的直接子提交，用其 SHA 填 `acceptanceAdmissionSHA`。正式 W0 要求该提交和收据已进入实际 main 的历史。
4. #119 按规定合并后记录实际 mergeSHA 和当时的 mainlineSHA。验证器核对标准二父合并、被测树、五个 GitHub Actions 原始作业与最新尝试、源码评审、包本体和每一格证据。主线前进后会检查实际产品树，合并后又撤回产品会阻止放行。

各 gate 的逐项字段与重放条件在 [gate107.py](gate107.py)。[合成回归测试](tests/test_baseline.py) 包含可运行的完整正例及伪造 PASS、错源码、缺 CI、跨 build、旧候选、跨图、复用操作和合并后回退等反例。正式记录中不得填入测试里的示例身份和观测。
